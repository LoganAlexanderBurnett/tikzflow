# Decisions

Architecture and process choices, with the reasons for them. Add new entries at the bottom. Don't rewrite old entries: if a decision changes, add a new entry that supersedes it.

## D1: Line endings and byte-exact test inputs (2026-10-06)
**Decision:** Set `* text=auto eol=lf` in `.gitattributes`, and mark `corpus/**` and `**/fixtures/**` as `-text`. The second pattern was originally `test/fixtures/**`; it was widened on 2026-10-07 to cover `spike/grammar/fixtures`.
**Why:** The round-trip tests are byte-exact. On Windows, git's line-ending conversion could silently rewrite test inputs, which would cause false failures or hide real ones. Real-world TikZ files sometimes use CRLF line endings, and preserving those must be tested too.

## D2: Default branch is `trunk` (2026-10-06)
**Decision:** The repo uses `trunk`, inherited from the local git config. It was the first branch pushed to GitHub.
**Why:** Recorded so that future sessions push to the right branch.

## D3: Round-trip testing checks byte coverage and minimal diffs (2026-10-07)
**Decision:** The round-trip checks are:
- the syntax tree's leaves cover every source byte exactly once;
- the share of each file that is modelled structure, rather than catch-all or error nodes, is reported;
- an incremental reparse matches a full parse;
- single edits change only the bytes they target, checked against golden files.

The byte-identical load/save check stays only as a cheap regression guard.

**Why:** The editor keeps the original text and patches it, so saving unedited code is byte-identical automatically and that check alone proves nothing. Content gets lost when part of the source isn't represented in the tree, or when an edit touches bytes it shouldn't. The new checks test for exactly that.

## D4: Evaluate TikZJax alongside busytex and SwiftLaTeX (2026-10-07)
**Decision:** Add TikZJax as a third candidate engine in Milestone 0.
**Why:** TikZJax already turns TikZ into SVG in the browser, using TeX compiled to WASM plus a DVI-to-SVG step. That matches our preferred SVG output for overlaying on the canvas. Even if we don't adopt it, its approach may be the best way to get SVG.

## D5: The grammar recognises known commands and leaves the rest opaque (2026-10-07)
**Decision:** The Lezer grammar recognises the TikZ commands it knows and sends everything else to catch-all or opaque nodes. It doesn't try to model TeX in full.
**Why:** TeX can't be parsed completely by a fixed grammar, because catcode changes and macro expansion can alter what the code means. This approach can never drop content, but it limits how much of an unusual file stays editable. The share of each file that is modelled is tracked so we can see that limit.

## D6: Plan for the Cloudflare Pages file-count limit, not only file size (2026-10-07)
**Decision:** Bundle TeX package trees into a small number of packs, each under 25 MB.
**Why:** Pages also caps the number of files per deployment. A TeX tree has thousands of small files, so splitting large files isn't enough. The exact limit is to be confirmed during Milestone 0.

## D7: Choose the project license only after engine licenses are confirmed (2026-10-07)
**Decision:** Milestone 0 confirms each engine's license. The project license recommendation waits until then.
**Why:** If we bundle a copyleft engine (SwiftLaTeX may be AGPL), it limits which licenses the project can use.

## D8: Large TeX assets stay out of git (2026-10-07)
**Decision:** Engine binaries and TeX Live packages go in a gitignored folder, and a cross-platform Node script fetches them. Whether production fetches them at build time or hosts them on R2 is decided in Milestone 3.
**Why:** GitHub rejects files over 100 MB, and keeping hundreds of MB of binaries in history would make the repo very large.

## D9: Every token is named, and tokens are contextual (2026-10-07)
**Decision:** The grammar names every token, including whitespace, comments and punctuation, so each byte lands in a named leaf. Each context has its own text token: document text, picture body, path, options, and coordinates. Keywords such as `at` and `node` are specialised only from the path-context word token, so the same word in a label stays plain text.
**Why:** With every token named, byte coverage can be checked mechanically: the leaves must tile the input. Contextual tokens keep keywords from leaking into labels and option values, and they let the grammar generate with no LR conflicts. The cost is more tree nodes, which is negligible at these sizes (a 28 KB picture parses in about 2.6 ms).

## D10: The parser is generated by the CLI, not a bundler plugin (2026-10-07)
**Decision:** `lezer-generator --typeScript` writes `parser.ts`, which is gitignored and regenerated by npm `pre*` hooks.
**Why:** Vite, Vitest, tsc and plain Node (which runs `.ts` directly) all see an ordinary TypeScript module, so the build doesn't depend on whether the Rollup plugin works with Vite 8 (Rolldown).

## D11: How engines are benchmarked (2026-10-07)
**Decision:**
- Each engine compiles one shared sample, `spike/engines/sample.ts`, that uses every required library.
- A probe reports the pgf version and each library's loaded flag (`tikz@library@<name>@loaded`), both in the log and as visible text.
- `scripts/bench-engines.ts` runs fresh-context Playwright trials in Edge (`msedge` channel, so no separate browser download). Download sizes come from files on disk, with Brotli at quality 11.

**Why:** Fresh contexts make "cold" mean an empty cache. Sizes are read from disk because Playwright can't return bodies of large worker requests, and compressing inside its response handler stalled the Vite server running in the same process. That bug briefly inflated TikZJax's cold compile to 9.7 s.

## D12: The dev server serves `vendor/` byte-for-byte, with cross-origin isolation (2026-10-07)
**Decision:** A Vite middleware serves `vendor/` raw. It never sets `Content-Encoding`, returns real 404s, and sends COEP/CORP headers on every response. The page itself is served with COOP/COEP.
**Why:** Vite's static server marked `.gz` files as gzip-encoded, so the browser inflated them before the engines' own decompressors saw them. Its `index.html` fallback also answered missing files with HTTP 200, so engines stored HTML as TeX files. Workers in a cross-origin-isolated page need COEP on their script responses. Production hosting must follow the same three rules.

## D13: Engine recommendation (APPROVED 2026-10-07)
**Status:** Approved by the owner after the follow-up checks: TikZJax, with our own build in Milestone 3 (see D15). The history below is kept for context.

The first approval was provisional, on condition of two timeboxed checks:

2. Confirm that TikZJax can load packages outside its format at compile time and can handle a user preamble with `\usepackage`, `\newcommand` and `\definecolor`.

The license question is settled by D14.

**Proposal:**

- **Don't ship busytex for now.** Revisit it, lazy-loaded, if Milestone 3 needs full TeX Live fidelity or user-supplied packages.
- **Drop SwiftLaTeX.**

**Why:**
- TikZJax is the only candidate that outputs SVG. It's small (3.8 MB Brotli) and fast (about 0.4–0.5 s per compile).
- busytex is faithful, but it needs 63 MB Brotli, its files are over the 25 MB limit, and it outputs only PDF.
- SwiftLaTeX failed within the timebox, is AGPL-3.0, has been inactive since 2022, and needs custom response headers.

**Questions raised in the M0 report (both resolved):**

- **Matrix-cell borders:** root-caused in the follow-up checks (PROGRESS.md); the proper fix is in D15.

## D14: The project license is GPL-3.0-or-later (2026-10-07)
**Decision:** The owner chose GPL-3.0, option (a) in the M0 report. `LICENSE` holds the official GNU text, and `package.json` declares `GPL-3.0-or-later`. This supersedes D7.
**Why:** The recommended preview pipeline uses the TikZJax fork (GPL-3.0+) and `dvi2html` (GPL-3.0), so a GPL-3.0 project can use them as they are. "Or later" matches the TikZJax fork and is the FSF's recommended form. It stays compatible with the GPL-3.0 dependencies, because the combined work is distributed under GPL-3.0. The owner confirmed the "or later" form on 2026-10-07.
**Consequences:** Every bundled component must be GPL-3.0-compatible, which the Milestone 5 license audit will check. LPPL, OFL, GUST, MIT, Apache-2.0 and public-domain components can all be combined with GPL-3.0 code. Pure GPL-2.0-only code could not, so any busytex binaries would need checking before they ship.

## D15: Requirements for our own TikZJax build (APPROVED for Milestone 3, 2026-10-07)
**Decision:** Don't ship the `@drgrice1/tikzjax` package as it is. Build our own variant of the pipeline: its `tex.wasm`, our own format, and a patched worker and driver. The owner approved this with amendments (marked **owner**). The build must:
1. **Run in GitHub Actions on Linux, not locally on Windows** (**owner**). The engine and format are built in CI and published as build artifacts.
2. **Build the format** from a pinned TeX Live snapshot: current LaTeX kernel, expl3 and pgf 3.1.12. Host the extra packages from the same snapshot as `tex_files/<name>.gz`, so they match the kernel.
3. **Replace `pgfsys-ximera.def` entirely** (**owner**). Its origin and license are unknown, so it must not ship. Use a driver whose license we know, based on pgf's own `pgfsys-dvisvgm.def` (LPPL). In that driver:
   - Inside TeX boxes, colour changes must set the stroke as well.
   - `stroke="none"` must apply only to glyphs.

   That fixes `\matrix` cell borders and pictures nested in node text. `dvi2html` must be adapted to the new driver's specials where they differ.
4. **Fix the file loader.**
   - Report missing files as missing, not as empty files.
   - Show a visible warning in the UI when a package isn't available (**owner**).
   - Accept uncompressed fetches as bytes, not strings.
5. **Always stream the log** through the `showConsole` messages, and use `\scrollmode` by default (**owner**), so errors give partial output plus line-mapped messages.
6. **Emit SVG sizes in bp,** or have the overlay scale by 72/72.27.
7. **Keep the fixed font set** (Computer Modern and AMS) for the preview. See D16.

**First Milestone 3 task (owner):** confirm the CI toolchain is feasible before anything else. That means building `tex.wasm` (web2js) and dumping a format from a pinned TeX Live snapshot with the new driver, on a Linux GitHub Actions runner.

**Why:**
- The requirements come straight from the M0 follow-up checks in PROGRESS.md.
- Building on Linux CI avoids Windows toolchain problems and makes the engine reproducible.
- A driver of unknown origin can't ship in a GPL project whose bundled components must all be license-audited (Milestone 5).

Until this is done, `fixBoxStroke()` and the 72/72.27 scaling are spike-only workarounds.

## D16: The preview always uses Computer Modern (APPROVED 2026-10-07)
**Decision:**
- The accurate preview always typesets in Computer Modern (plus the AMS fonts).
- `.tex` export keeps the user's preamble, including any font packages, unchanged.
- When the preamble loads a font package, the UI shows a small notice that text widths in the preview may differ from the user's document (Milestone 3).

**Why:** The TikZJax pipeline renders text with web fonts that need matching TeX metrics and per-encoding glyph maps. Supporting arbitrary font packages would mean converting each font family. Computer Modern keeps the preview fast and small, and the notice stops users from trusting text widths the preview can't promise.


## D17: The semantic layer always works from a full parse (2026-10-07)
**Decision:**
- CodeMirror's incremental parse is used only for syntax highlighting.
- Every time the text changes, the semantic model (nodes, edges, styles) is rebuilt from a full parse.
- The round-trip tests require an incremental parse to match a full parse exactly whenever the document has no parse errors. With errors, the incremental parse must still cover every byte.

**Why:**
- Over 12,500 chained random edits to the corpus, incremental and full parses never differed on error-free documents.
- On documents with errors they differed about 0.6% of the time. Lezer's error recovery can settle differently when it reuses nodes from the old tree.
- A full parse is cheap: about 2.6 ms for a 28 KB picture.
- Rebuilding from a full parse means the model never depends on edit history. Reloading a file always gives what typing it gave.

## D18: Error nodes can hold bytes without leaves of their own (2026-10-07)
**Decision:** The byte-coverage check treats bytes inside an error node (`⚠`) that none of its children cover as covered by the error node itself. They count as error bytes. A gap anywhere else is still a coverage failure.
**Why:** During recovery, Lezer skips characters that no token valid in the current context can match, such as a `;` inside an unclosed coordinate. It puts them inside the error node's range but gives them no child node. They are still represented, as an error, and since the editor never re-serialises the tree, they can't be lost. Random mutation testing of the extended grammar found this case. The M0 fixtures never hit it.

## D19: Grammar additions for real-world flowcharts (2026-10-07)
**Decision:** The grammar moved from `spike/grammar/` to `src/parser/` and now models the constructs that the TeX.SE corpus showed are common:
- `\tikzstyle{name}=[...]`, including `+=` and the brace-less form.
- Picture options as their own `PictureOptions` node. A precedence marker resolves the conflict with a leading Opaque `[...]`.
- `{...}` in a picture body as `BodyGroup`, with nested statements. `bodyGroupRole()` in `src/parser/structure.ts` decides from context whether the group is a scope or an argument of an unknown command. `\begin{scope}` and `\end{scope}` stay flat markers, which the semantic layer pairs up.
- `\foreach` and `\matrix` as their own nodes (`Foreach`, `MatrixStatement`). Everything inside them is opaque.
- Pictures inside document-level groups, such as `\resizebox{...}{!}{...}`.
- `-|` and `|-` inside coordinates without spaces (`(a.north-|b)`).
- `;` inside braced option values (`pic code={...;}`).
- Path continuations after `\coordinate`, `at` after a path `coordinate`, and the path keywords `rectangle`, `circle`, `ellipse`, `arc` and `grid`.

**Why:** On 431 TikZ blocks from TeX.SE flowchart answers, these were the constructs that produced parse errors, or left modelled content opaque. After the change, no corpus file has a parse error except the deliberately broken one.

**Decision:**

## D21: UI stack: Preact with signals, CodeMirror 6, KaTeX (2026-10-07)
**Decision:** The app uses:
- Preact 11 with `@preact/signals` for state;
- CodeMirror 6 for the code pane, with the TikZ Lezer grammar for highlighting;
- KaTeX for math in labels.

All three are MIT-licensed; KaTeX's fonts are OFL. JSX is compiled by Vite's own transformer (`oxc.jsx.importSource = "preact"`), so no framework plugin is needed.
**Why:** SPEC.md allows Preact, Svelte or no framework. Svelte needs a compiler plugin, which is a risk with Vite 8 (Rolldown). The canvas re-renders on every drag frame, so derived state is best expressed with signals.

## D22: Label sizes come from Computer Modern metrics, not the browser (2026-10-07)
**Decision:**
- Text in labels is measured with KaTeX's metric tables (`src/text/fontMetrics.ts`, generated by `npm run gen:font-metrics`). These tables come from the Computer Modern fonts.
- Math is measured from KaTeX's box tree (`__renderToHTMLTree`), which carries per-glyph widths.
- The browser only draws the labels: HTML in `foreignObject`s, placed on baselines measured once the fonts load.

**Why:**
- Node sizes decide positions (`below=of a` depends on a's height). Those sizes must be identical in tests and in the browser, and must not change when fonts finish loading.
- TeX's metrics are what pdfTeX uses, so sizes match (D23).
- It also matches D16: the preview uses Computer Modern.

## D23: The interpreter follows TeX, checked with pdfTeX (2026-10-07)
**Decision:** `npm run fidelity` compiles every corpus picture, plus targeted probes in `spike/engines/probes/`, with busytex (pdfTeX). TeX prints each named node's compass anchors, which are compared with the native layout. Each rule below was confirmed this way:
- **Key order matters for the positioning library.** "on grid" and "node distance" apply only if they come before `below=of a`. The old `below of=` syntax reads them at the end.
- **Scale doesn't reach nodes.** Positioning distances and a node's own xshift and yshift ignore the picture's `scale`, because nodes keep only the translation. `transform shape` scales the node, its text and those distances. `at` coordinates are always scaled.
- **Fonts in lengths.** `em` in node keys (minimum height, text width, inner sep) means the document font, never the node's `font=`.
- **Label boxes are natural.** First line's height, last line's depth, lines `\baselineskip` apart. No struts, with or without `text width`. Interword spaces may shrink by a third when wrapping.
- **Old-syntax diagonals.** `below left of=` moves node distance along the 45° line.
- **Chains.** A chain node is placed when `on chain` runs, so a later `on grid` doesn't apply to it.
- **Class font.** The document class's size option (10, 11 or 12 pt) sets the base font.

Result: of 271 corpus nodes in the 22 pictures pdfTeX compiles, 200 centres are within 1 pt and 247 within 3 pt. Sizes: 218 are within 1 pt. Remaining differences: TeX's hyphenation and paragraph line breaking, math line breaks after relations, and shapes drawn as rectangles (single arrow, rectangle split). Text rotated by `\rotatebox` is drawn unrotated.

**Why:** Visual edits are checked by laying out the patched text again (D24). That check only proves the edit agrees with our interpreter, so the interpreter has to agree with TeX. These rules are invisible from the TikZ manual's examples. Guessing them caused errors of 30–190 pt before the check existed.

## D24: How a drag becomes code (2026-10-07)
**Decision:**
- **Snapping** (`src/edit/snap.ts`) lines the node's centre up with other nodes and snaps gaps to the node distance.
- **Emitter.** On drop, `src/edit/move.ts` writes the first of these that reproduces the dropped position:
  1. a straight relation at node distance: `below=of a`;
  2. a perpendicular coordinate when lined up with two different nodes: `at (a |- b)`;
  3. a straight relation with a written distance, up to 5 cm: `right=1.5cm of a`;
  4. the node's previous relation, plus `xshift`/`yshift` if it moved off the axis but still overlaps;
  5. a diagonal relation to a node within 3 cm: `below right=5mm and 1cm of a`;
  6. a straight relation to a nearby node plus a shift;
  7. plain coordinates.
- **Plain-coordinate files.** A node placed with plain numbers keeps numbers unless the drop lines up with other nodes, so TikZiT-style files stay that way.
- **Relational `at`.** A node placed with `at (a -| b)` keeps it and gets a shift.
- **What can be referenced.** Only nodes defined earlier in the code (TikZ requires it), that don't depend on the moved node, and whose names are written in the source (not implicit chain names). When a drop lines up with a node defined later, the status bar says so.
- **Distances** are rounded to whole millimetres.
- **The patch** replaces the node's placement option in place, adds or removes `at`, and never touches other bytes of the statement. Comments stay.
- **Verification.** Each candidate is checked by laying out the patched text. Only a candidate that lands where it was dropped is used.

**Why:**
- SPEC.md's priority order puts relative positioning first and perpendicular coordinates second. Here the perpendicular form ranks above a relation with an arbitrary written distance. When a node lines up with two nodes, `at (a |- b)` keeps both alignments if either moves. A written distance keeps only one, by coincidence.
- The "previous relation plus shift" rule keeps nudges minimal and local. Without it, a 5 mm nudge was written relative to a node 6 cm away.
- **Owner decision requested:** confirm this ordering.

## D25: One undo history for both panes (2026-10-07)
**Decision:**
- The CodeMirror document is the only state that undo restores.
- Canvas edits are dispatched as CodeMirror transactions with `isolateHistory`, so each drag is one undo step that never merges with typing.
- Ctrl+Z, Ctrl+Y and Ctrl+Shift+Z call CodeMirror's undo and redo when the canvas has focus. Selection isn't part of the history.

**Why:** The text is the source of truth, so undoing the text undoes the visual edit too. A separate visual history could disagree with the code.

## D26: What "kept as-is" and "locked" mean in M1 (2026-10-07)
**Decision:**
- **Opaque blocks.** `\foreach`, `\matrix`, unknown commands and syntax errors are opaque blocks. They're kept verbatim, marked in the code pane, and not drawn natively until the TeX preview arrives in M3.
- **Unknown options don't lock a node.** Examples are `drop shadow`, `decorate`, and keys from libraries we don't model. They're kept in the code and listed in the summary as "options the preview ignores". The node stays draggable.
- **Locked nodes.** A node is locked only when its position can't be rewritten safely:
  - fit nodes, chain nodes and path labels or coordinates;
  - names containing macros;
  - positions relative to something inside an opaque block or something unresolvable.

**Why:** SPEC.md says unknown options become locked opaque blocks. Locking every node with an unmodelled cosmetic option would lock most real-world flowcharts, for example every node in `se-194593-styled-colors.tex`, because of `drop shadow`. The option itself is still never edited or lost. Only placement needs to be understood to move a node.

## D27: The whole document stays in the code pane (2026-10-07)
**Decision:**
- Pasting or opening a full `.tex` document keeps all of it in the code pane.
- "Extracting" the picture and preamble parts means the model reads them (styles, `\tikzstyle`, libraries, `\definecolor`, simple `\newcommand` macros) from the text in place.
- Documents with several pictures get a picker.
- Definitions only apply to pictures after them.

**Why:** Cutting the picture out of the document would lose everything else in it. Keeping the document also keeps load and save byte-identical.

## D28: Relational moves load the positioning library (2026-10-07)
**Decision:**
- When a move writes `=of` positioning and the document has a preamble without the `positioning` library, the same edit adds it. It goes into the last `\usetikzlibrary` before the picture, in that list's separator style. With no such line, `\usetikzlibrary{positioning}` goes after `\usepackage{tikz}` or the `\documentclass` line.
- `chains` and tikz-ext's `ext.positioning-plus` count as loading `positioning`.
- A bare picture (no preamble) gets a note instead, unless it already uses `=of`.
- The summary also warns when a shape's library isn't loaded.

**Why:** Without the library, `below=of a` is a compile error. Full library management is Milestone 2; this is the part M1's emitter needs to produce valid code.

## D29: File encodings (2026-10-07)
**Decision:**
- Files are decoded as UTF-8, keeping any byte-order mark as U+FEFF.
- UTF-16 is recognised by its byte-order mark.
- Anything else is read as ISO-8859-1, which maps every byte to one character and so round-trips any 8-bit encoding.
- Saving re-encodes in the file's own encoding. If a typed character doesn't fit ISO-8859-1, the download falls back to UTF-8 with a message.

**Why:** Byte-identical load and save is a hard requirement, and real `.tex` files still use `inputenc[latin1]`. `TextDecoder` alone would replace invalid bytes with U+FFFD and lose them.

## D30: Golden minimal-diff tests (2026-10-07)
**Decision:** `test/golden.test.ts` scripts two moves per corpus picture:
- snapping a node below an earlier node at node distance;
- nudging the last editable node by (5 mm, −3 mm).

For each move it checks that:
- the output matches `test/fixtures/golden/*.tex` byte for byte, in the file's encoding;
- every changed byte lies inside the node's statement (apart from loading `positioning`, D28);
- the node lands where it was dropped;
- every node that doesn't depend on it stays exactly in place.

Goldens are regenerated with `UPDATE_GOLDEN=1` and reviewed with `npm run golden:review`.
**Why:** This is SPEC.md's "single edits must produce minimal diffs, checked against golden files". The placement and dependency checks catch wrong edits that a byte comparison alone would happily record. The dependency check found a real bug: cycle protection had been seeing no dependents.

## D32: Milestone 2 is split into 2a (nodes and styles) and 2b (edges) (2026-10-07)
**Decision:** Each part ends with its own report and approval checkpoint.
- **2a, nodes and styles:**
  - first, the fixes from M1 testing (D33);
  - the shape palette and keyboard creation;
  - in-place label editing;
  - resizing;
  - the properties panel with node-or-style scope;
  - multi-select;
  - the style panel;
  - library management.
- **2b, edges:**
  - anchors that stay attached;

## D33: Requirements from the owner's test with a real research figure (2026-10-07)
**Decision:** The owner tested M1 with a 27-node research figure, added as `corpus/self-hybrid-surrogate.tex` with its own code errors left in place. These requirements were added to Milestone 2a in SPEC.md.

Fixes to M1 behaviour:
- **Locked nodes explain themselves in plain language.** For an unresolved reference, the explanation says LaTeX would fail on it too. It offers one-click fixes: "Pin at current position" (absolute coordinates) or "Attach to another node".

## D35: The shared editing core (2026-10-07)
**Decision:** Every 2a edit is built from these helpers in `src/edit/`.
- **Option edits** (`optionEdits.ts`, `setOption`):
  - Setting a key replaces its *last* occurrence, which is the one TikZ applies. With no occurrence, the key is appended to the last list in that list's separator style. A list laid out one item per line gets the new item on its own line.
  - An item that uses a style argument (`#1`) is never edited; the edit is refused.
  - Values containing top-level `,`, `=` or brackets are braced.
- **Style edits** (`styles.ts`):
  - **Where styles are defined.** A picture's styles come from three kinds of site, in reading order: the preamble before it, its own options, and `\tikzset`/`\tikzstyle` at the top level of its body. Definitions inside scopes aren't edit targets.
  - **Which definition is edited.** A style's current definition is its last `.style` plus any `.append style` after it, and edits go to that chain.
  - **Emptied styles** keep their braces: `name/.style={}`.
- **New styles** go to the site holding the most definitions; on a tie, the one closest to the picture. A `\tikzstyle` file gets `\tikzstyle` lines in its own spacing and brace form. Otherwise:
  - a document gets a new `\tikzset` after its last `\usetikzlibrary` (or `\usepackage{tikz}`, or `\documentclass`);
  - a bare picture gets the style in its own options.
- **Libraries** (`libraries.ts`):
  - **Adding.** Edits name the libraries they need, and `ensureLibraries` adds them all in one change.
  - **New lines.** Inserted lines now start with the line ending (`\n\usetikzlibrary{…}` at the end of the anchor line) rather than ending with it. The resulting text is the same.
  - **Removal** follows D34. Usage patterns exist for positioning, the shapes libraries, arrows.meta, fit, backgrounds and calc. The patterns are deliberately generous: a false match only keeps a library loaded.
  - **Whole lines.** A `\usetikzlibrary` whose list would become empty is deleted with its line.
- **Inserting statements** (`insert.ts`):
  - **Placement.** New nodes go after the picture's last top-level node and new edges after its last top-level path. They are never inside a scope or layer, whose options would apply to them. If every path comes before the new node, its edge goes right after the node.
  - **Format.** Each statement goes on its own line with the anchor line's indentation and the file's line ending.
  - **Syntax errors.** Nothing goes right after a statement containing a syntax error, because an unclosed brace there would swallow the new code (found by the corpus sweep on `self-broken.tex`). If the node a new one must follow is broken, the insertion is refused.
- **Node names** (`names.ts`):
  - **Words.** Up to three words from the label, with TeX markup, math and accents stripped and small words such as "the" dropped. A name never starts with a digit.
  - **Naming style.** Names follow the document's style (camelCase, snake_case or kebab-case, by majority), defaulting to camelCase, which the corpus uses most.
  - **Taken names.** A name counts as taken if it's laid out, inside a block kept as-is, a bounding box, or written as `(name)` or `name=` anywhere in the picture.
- **Selection** is one or more nodes (the last clicked is the primary), or one path. Shift-click toggles a node in or out. Every selected statement is highlighted in the code.

**Why:**
- These are the primitives that the properties panel, the palette, keyboard creation, resizing and the style panel all share. Each changes only the bytes it is about.
- A sweep in `test/edit-core.test.ts` defines a style, inserts a node using it and connects it, on every corpus picture with a named node (27 pictures). Nothing else moves, and the parse doesn't get worse.

**Note for step 6:** a picture can reuse a node name (`se-102785-foreach-scope.tex` defines `a` twice). A new node placed after the second definition refers to the second one. Creation must insert right after the parent when its name is reused later, and verify by layout.

## D37: The properties panel (2026-10-07)
**Decision:**
- **Panel.** A panel to the right of the canvas shows the selected nodes. It has the lock explanation (D36) when the primary node is locked, then the properties: fill, outline and text colour, font (size, bold, italic, family) and alignment. With nothing selected, it says how to select. Paths get their panel in M2b.
- **Scope** is a radio group at the top, as D34 asked. "This node" (or "These N nodes") is the default, and every new selection starts there again.
  - **Style options.** Styles that every selected node names directly are offered as "All state nodes (14)". The count includes nodes that use the style through another style.
  - **Unwritable styles.** A style the editor can't write (an unsupported form) is shown but disabled, with the reason.
- **Reading values** (`src/edit/properties.ts`). The panel follows the document's styles the way TikZ applies them: "every node" first, then the node's keys in order, with each named style's chain expanded where it is named.
  - **Labels.** A value from a style is labelled "(from control)". Values that differ across the selection show "Mixed".
  - **Swatches** come from the laid-out node, so they show what is drawn.
- **Writing values.** Each node or style gets one `setOptions` call. It replaces the last item for each key in place and appends the rest together in the list's own separator style. Several selected nodes make one undo step. An item that uses a style argument (`#1`) is never edited; the whole edit is refused and says so.
  - **Colours** write `fill=`, `draw=` and `text=`. "None" writes `none` for fill and outline.
  - **Fonts** write the whole font, because a later `font=` replaces an earlier one. With `control` giving `\small`, bold on the node writes `font=\small\bfseries`. Other commands in the value (`\color{…}`, `\scshape`) are kept where they are.
  - **Undoing a font change.** A node whose font goes back to what its style gives loses its own `font=` item. Turning off a font the node only inherits writes `font={}`.
  - **Alignment** writes `align=`. Justify on a node without a text width also sets one: the text's current width, rounded up to whole millimetres. The status bar says so. On a style without a text width, Justify is disabled and its tooltip says why.
  - **Style scope** reports nodes that set the key themselves and so keep their value: "1 of the 2 process nodes set their own fill".
- **Colour picker** sections, in order:
  - the document's own `\definecolor` and `\colorlet` names, before and inside the picture;
  - common xcolor mixes, light and dark;
  - the base colours, and None;
  - a custom colour. It can be named and added as `\definecolor` in one undo step, or used without a name as `{rgb,255:red,…;green,…;blue,…}`.
- **New `\definecolor` lines** go after the document's last colour definition, in the same colour model (`{RGB}{31,119,180}` next to RGB definitions). Otherwise they go in the preamble after `\usetikzlibrary`, or at the start of a bare picture's body. Names must be letters and digits and not already a colour.
- **Interpreter fix.** A later `font=` now replaces an earlier one instead of adding to it, from the document's font. pdfTeX confirmed it with the new probe `spike/engines/probes/p3-font-replace.tex`, where `[big, font=\bfseries]` is normal size. No corpus node changed. Font editing depends on this.

**Why:**
- Following styles, rather than reading only the node's own options, is what makes "This node" changes correct. It also lets the panel show where a value comes from.
- Writing whole fonts and dropping redundant `font=` items keeps the code as a person would write it.
- Named colours and in-place edits keep generated code hand-written in style (SPEC.md, "Human-quality output").

## D38: Resizing nodes (2026-10-07)
**Decision:**
- **Handles.** One selected node shows eight handles (corners and sides), unless it can't be resized: a `fit` node (its size follows what it fits), a node scaled with `transform shape`, or a shape the preview only approximates (`star`, `cloud`, …). Resizing is for one node at a time.
- **A node grows around its anchor,** as in TeX. The dragged edge follows the pointer: a node placed with `below=of a` (anchor north) keeps its top edge and grows downward, and a centred node grows both ways, so the pointer moves half as far as the width changes (D38's `edgeShare`). The size change is never paid for by editing the node's position.
- **What is written** (`src/edit/resize.ts`, `planResize`):
  - **Width and height:** `minimum width` and `minimum height`, in whole millimetres (`5mm`, `2.5cm`, never `86.0000007pt`). An existing item is replaced in place; otherwise the item is appended. Asking for less than the natural size writes nothing, or lifts a minimum that a style gives down to the natural size.
  - **Rewrap:** a node that already has a `text width`, or whose label can break at a space, gets `text width` instead when the drag makes it narrower than its text. The text width never goes below the widest unbreakable word. A single word never gets one.
  - **Circles** get `minimum size`.
  - **Shapes with a text width** (rectangle, rounded rectangle, tape, trapezium, cylinder) can rewrap. Diamonds and ellipses only take minimums, because their width isn't text width plus padding.
- **Checked by layout.** The patched text is laid out again. If the drawn size is off by more than 0.75 mm (a rounded rectangle's width depends on its height, for one), the written value is corrected by the error, up to twice. If the size doesn't change at all, the drag is refused with the reason, for example a later `minimum size` or, in style scope, a node that sets its own size.
- **Snapping.** The size snaps to whole millimetres and to the width or height of another node (within 7 px of the dragged edge). Alt drags without snapping to other nodes. A match is marked with a dimension line on both nodes and named in the status bar ("Same width as start").
- **Live preview.** Each new millimetre during a drag lays out the patched text (`resizePreview` in the store), so dependent nodes and edges follow. The edit is applied once, on release, as one undo step.
- **Scope.** A resize follows the properties panel's scope (D34, D37): "This node" by default, or the chosen style ("All process nodes"), whose body gets the `minimum width` and so changes every node using it. The scope signal moved from the panel into the store (`scopeStyle`, `activeScope`) so the canvas can read it. Nodes that set their own size keep it, and the status bar says how many.
- **Sizing data.** `LaidOutNode.sizing` holds the natural size, the minimums in effect, the text width and a function for the widest word.

**Also in this step** (feedback on steps 2–3):
- **Drag to pin.** A node locked only by an undefined or later-defined reference can be dragged. Dropping it pins it with plain coordinates at the drop position (`planPin(…, center)`). Snapping and guides work as usual. The panel's "Pin at current position" button stays.
- **Collapsible panel.** The properties panel folds into a 30 px strip. The state is remembered per viewer in `localStorage`.

**Why:**
- Growing around the anchor is TikZ's own behaviour and keeps the diff to the size items; moving the node to hold the opposite edge would mean rewriting its position on every resize.
- Whole-millimetre values and in-place updates keep the code as a person would write it, and repeated resizes don't pile up items.
- Following the panel's scope keeps one rule for every change: it applies to this node unless "all state nodes" is chosen.

## D39: Editing labels in place (2026-10-07)
**Decision:**
- **Double-click** a node (or press F2 with it selected) to edit its label. A text box opens over the node holding the TeX between the label's braces, exactly as written (`Return\ $n \cdot f(n-1)$`), not a rendered version. Enter applies it, Shift+Enter adds a line, Escape cancels, and clicking elsewhere applies it.
- **Patch.** Only the characters that differ are replaced (`src/edit/label.ts`, `planLabelEdit`): changing "world" to "there" in `{Hello world}` is a five-character change. Comments and line breaks inside the label stay. In a file with CRLF line endings, new lines are written as CRLF.
- **What is refused,** with the reason shown under the box and in the status bar. The text box stays open, so nothing typed is lost:
  - unbalanced braces (`\{` and `\}` are fine);
  - a `%` with no line break after it, which would comment out the closing brace;
  - a trailing backslash, which would escape it.
  If the label is applied while one of these holds (clicking elsewhere), the edit is dropped and the status bar says "Label not changed".
- **Checked by parsing.** The patched text must still contain the same node with the label as written, the same number of nodes, and no new syntax errors. Anything else is refused as changing the structure of the code.
- **Which nodes.** Any node with a closed label, including locked ones: a label edit doesn't touch position. Not coordinates, unclosed labels, or edge labels (those come with edges in 2b).
- **Undo.** One undo step, in the shared history. While the text box has focus, Ctrl+Z undoes the typing in the box; the app-wide shortcut now ignores text boxes, selects and inputs.
- **No live preview while typing:** the box covers the node, and the canvas updates when the label is applied.

**Also fixed:** the canvas never took keyboard focus, because Preact writes `tabIndex` on an SVG element as a case-sensitive attribute the browser ignores. It's `tabindex` now. F2 needed that.

**Why:**
- Labels often hold macros, math and font commands. Editing the TeX keeps all of them and keeps the diff to the characters typed, which is the project's rule.
- The parse check turns "the user typed something odd" into a refusal rather than a broken statement, in the same spirit as checking moves by laying the result out.

## D40: Resizing holds the opposite edge (2026-10-07)
**Decision:** This supersedes D38's rule that "a node grows around its anchor" and that its position is never edited. The owner asked for PowerPoint/Figma behaviour:
- **The edge or corner opposite the handle stays where it is,** and the dragged edge follows the pointer one for one. With Ctrl (Cmd on a Mac) the centre stays and both edges move. Alt is already "no snapping", and Shift is kept for Shift-click multi-select and a possible proportional resize later.
- **Where the anchor already holds that edge, only the size is written.** A node placed with `below=of a` (anchor north) dragged by its south side gets `minimum height` and nothing else.
- **Otherwise the node is repositioned in the same edit** (`holdEdge` in `src/edit/resize.ts`). The size is written first and the picture laid out again, because the drawn size is rounded to whole millimetres. The move planner (`planMove`, D24) is then asked for the centre that puts the held edge back, so the position stays relational where it can: `below=of small` becomes `below=of small, xshift=4mm`, and a node at `at (2,1)` gets new coordinates. Its relation is kept as written when the gap is the node distance; the planner now leaves out the distance in that case instead of spelling it out (`below=8mm of small`).
- **One undo step.** The two edits are merged into one set of changes against the original text (`composeChanges`, using CodeMirror's `ChangeSet`), so one Ctrl+Z undoes size and position together.
- **A size-only fallback, with a note,** when the node's position is locked (an undefined reference, say) or the planner can't improve on it: the node then grows around its anchor as before and the status bar says the opposite edge moves.
- **Scope.** Under "All process nodes" the style gets the size and every node using it changes; the dragged node alone is repositioned to hold its edge. The other nodes grow around their own anchors.
- **Precision.** Shifts are written in whole millimetres like every emitted distance, so with a relational position the held edge can be up to 0.5 mm off. Plain coordinates are written to 0.01 of their unit (0.1 mm for centimetres). Circles hold on the dragged axis and stay centred on the other.
- **Snapping to other nodes' sizes** is now one for one with the pointer (it used a share of the pointer movement before).

**Also fixed:** the canvas refitted the view after every edit that changed the picture's bounds, because the fit effect read the layout and so subscribed to it. A resize that made the picture larger rescaled the view under the pointer. `fit` now reads the layout without subscribing, so only a fit request or a change of canvas size refits. This was in M1.

**Why:** Growing around the anchor made the node's far edge move when it was centred, which is not what a drag on a corner means. Using the move planner keeps the output looking hand-written, and merging the edits keeps one drag one undo step.

**Also:** the properties panel shows an unnamed node's label (cut to 28 characters) instead of "Unnamed node". `resizePreview` became `previewLayout`, since creation uses it too.

**Why:**

## D42: The style panel, factoring repeated options, and Match width/height (2026-10-07)
**Decision:**
- **Style panel** (`src/edit/styleedit.ts`, `src/ui/stylepanel.tsx`). A "Styles" section at the bottom of the properties panel lists every style the picture defines (TikZ's `every …` styles left out) with how many nodes use it, directly or through another style.
  - **Select** selects those nodes. **Edit** opens the body, the text between the definition's braces (or `\tikzstyle`'s brackets), as written.
  - **Applying** replaces only the characters that differ, like a label edit (D39). The text is refused if it has unbalanced braces, a `%` that would comment out the closing brace, a trailing backslash or (for a bracket body) a stray `]`. The patched code is parsed again, and the style names, node count and number of syntax errors must be as before.
  - **Not editable here:** a style with an argument (`#1`) and forms the editor doesn't understand. Each says why. Later `.append style` definitions stay as written, and the panel says so.
- **Repeated options** (`findRepeats`). Sets of two or more options that at least two nodes write out in full, with at least six items in all (three nodes with two options, two nodes with three), and no larger set shared by as many nodes. Only appearance counts: placement, names, labels, `fit`, `rotate`, document styles and the like are left out. The best six are offered.
  - **Factoring** (`planFactor`) defines the style (D35: where the document keeps its styles) with the items in the first node's order. In each node the first repeated item gives its place to the style name and the others are removed, comments and other items staying where they are.
  - **Checked by layout.** Every node of the patched picture must look exactly as before: shape, position, size, colours, line, text. If an option between the repeated ones would override one, nothing is written and the status bar names the node. That case is `[rounded corners, fill=red, fill=blue!10, draw]`, where moving `fill=blue!10` to the front would let `fill=red` win.
  - **Names** are suggested from the fill colour (`blueBox`) or the shape (`diamondNode`), and refused if they are taken, malformed, or a TikZ key or shape (a style called `diamond` would shadow the shape).
- **Match width and Match height** (`planMatch` in `src/edit/resize.ts`). With two or more nodes selected, the properties panel offers both. They give the other nodes the first one selected's width or height.
  - **"This node" scope:** each other node gets its own `minimum width` or `text width` through `planResize`, in whole millimetres, as in D38. Nodes already that size are left alone; nodes that can't be resized (a `fit` node, say) are skipped with a note. They grow around their anchors, as TeX draws them, so a stack stays a stack. Dragging a handle holds the opposite edge (D40); matching doesn't.
  - **Style scope:** the style takes the size, so every node using it matches (nodes that set their own size keep it, and the status bar says so).
  - One undo step either way.

**Why:**
- Editing the text of a style keeps whatever the author wrote (macros, comments, odd keys) and still updates every node, which is the point of a style. A structured editor for style bodies would be a second place that has to understand every key.

## D46: The edge model (M2b step 1, 2026-10-07)
**Decision:**
- **Routes.** The layout records, for every path, the points it goes through (`RouteStop`: the coordinate's source range and text, the node it names, its anchor, whether it is bare or relative) and the pieces drawn between them (`RouteSeg`: line, `|-`/`-|` corner, or curve, with the operation and control points that drew it). Geometry is kept before arrow-tip shortening. A route is marked when the path also draws shapes (`rectangle`, `circle`, `arc`, `cycle`, …) or has something the interpreter can't follow.
- **Edges** (`src/model/edges.ts`) are a path's route split at every node with a shape it passes through: `\draw (a) -- (b) -- (c);` is two edges, `(a) -- (1,1) -- (c)` is one with a waypoint, and each `edge` operation is its own. Coordinates (`\coordinate`) are waypoints, not ends. An edge can end at a plain point (`(a) -- ++(1,0)`). Paths that draw nothing (`\path`) have no edges.
- **Mode** comes from how the edge is written: any curve is "curved", any `|-`/`-|` is "orthogonal", several pieces are a "polyline", otherwise "straight".
- **Labels** belong to the edge whose operation comes last before them in the code, so `(a) -- node {x} (b)` and `(a) -- (b) node[pos=.5] {x}` both label a → b.
- **Locked edges** (shapes, or code the editor can't follow) can be selected and say why in the panel; they are never rewritten.
- **Selection** gains an edge kind. Clicking an edge, one of its labels, or putting the cursor in its code selects it; a path with one edge highlights its whole statement, otherwise only that edge's part. Paths without edges (chain joins, `\path`, shapes) are still selected as a whole and the panel says what they are.
- **Edge ids** are the path's position plus the edge's index (`path@412:1`). An edit maps a selected edge's id through its changes (`mapPathId`), so the edge stays selected after code before it changes.
- **Edge labels** are edited in place like node labels (double-click, D39), with the same refusals and parse check.
- **Interpreter fix.** A coordinate with no operation before it now moves instead of drawing: `\draw (a) -- (b) (c) -- (d);` no longer draws b to c. TikZ has always worked this way; no corpus picture or golden file changed.
- **Unnamed parents (D44).** Tab, Enter or a palette click on a node with no name gives it one in the same edit, from its label (then its style, then its shape), written as ` (name)` after its options. The parent is named first, so it keeps the plainer name when both labels would give the same one.

**Why:** Every later 2b step (anchors, vertices, modes, labels, properties, delete) edits one edge's code. Tying each point and segment to its source range is what lets those edits change only that edge's bytes.

## D47: The edge-editing core and how points are written (M2b step 2, 2026-10-07)
**Decision:** Every edge edit goes through `src/edit/edges.ts`.
- **What an edit changes.** It replaces the text of some of a path's points (`writeStops`); later steps add operations. Nothing outside that path's statement changes.
- **How a point is written,** in SPEC.md's emitter order as it applies to a point on a path:
  1. **An end** goes to a node's anchor (`(b.west)`) or its bare name for the border (step 3).
  2. **A perpendicular coordinate** when the point lines up with the centre line or a side of two different nodes defined before the path: `(b |- a)`, `(a.east |- b.north)`. The edge's own end nodes are preferred.
  3. **Relative to the point before it**, `++(8mm,0)`, so it follows its nodes. A `+` point stays `+` (it doesn't move the point later ones are measured from). Lengths are whole millimetres (D44), written in the picture's own style: plain numbers (`++(0.5,0)`) when the picture's relative points are written that way, otherwise `mm`/`cm` (10 mm and more as `cm`, as `formatDistance` does).
  4. **Plain coordinates** last, in the path's units to 0.01 of a unit. A point already written with plain numbers keeps them unless it lines up with two nodes, as for nodes (D24).
- **A waypoint is never written as a node's anchor.** The path would then pass through that node, and it would read as two edges (D46).
- **The path's own frame.** Routes record the path's transformation and unit vectors, so `\draw[scale=2]` gets `++(1.5,0.5)` for a 3 cm by 1 cm move.
- **Other points stay put.** Relative points later in the path that are measured from a point that moved are rewritten so they stay where they were. They are written to 0.1 mm, since they hold a position someone else chose. Everything else in the path must stay exactly in place.
- **Checked by layout.** The patched text must have no new syntax errors and the same nodes in the same places (coordinates on the path itself excepted), and every other path must draw exactly as before. A written point must land within whole-millimetre rounding of where it was dropped (0.5 pt for perpendicular coordinates). Anything else is refused with the reason. One case this refuses: a path that defines a coordinate another path uses (`coordinate (corner)`), because moving it would move the other path. Two corpus waypoints hit it; the other 32 move.
- **The node a `\node ... edge` path starts from** is the node statement itself, and an edit can't rewrite it.
- **Snapping** (`snapWaypoint`) lines a point up with the centre lines and sides of nodes it may refer to, and level or plumb with its neighbouring points so segments come out straight, with guides.
- **Fidelity probe.** `spike/engines/probes/p4-edge-waypoints.tex` checks 16 path points against pdfTeX: `++` after a bare node starts from its centre; `+` keeps its base; perpendicular points with anchors; `pos` on `|-` and `-|`; a coordinate with no operation before it moves (D46's fix); and a path's `scale` applying to relative points with and without units. All 16 are within 0.01 pt.

**Why:** Writing points relationally keeps edges attached when nodes move, which is the first 2b item. Holding the other points and checking by layout is the same safety net as moves (D24) and resizing (D40).

## D48: Anchors, reconnecting and drawing edges (M2b step 3, 2026-10-07)
**Decision:**
- **End handles.** The selected edge shows a handle at each end. Dragging one shows the node under the pointer with its eight compass anchors, and the edge redrawn as it would be written (a preview layout, as for resizing). Dropping writes the end:
  - on an anchor dot (within 9 px): `(b.west)`;
  - anywhere else on the node: the bare name `(b)`, so the path meets the border pointing at the other end;
  - on another node: the same, which reconnects the edge;
  - on empty canvas: nothing, with a note.
- **Only that end's text changes** (`planEnd`), through the step 2 core: relative points after it are held where they were, and the result is checked by layout. One undo step.
- **Refused, with the reason in a tooltip and the status bar:**
  - **A node defined after the edge's code.** TikZ can only refer to nodes defined earlier.
  - **An end shared with the next edge in the same `\draw`** (`b` in `(a) -- (b) -- (c)`). Moving it would move that edge too, against D45. Splitting the statement would change the arrow tips (one `->` tip becomes two), so it isn't done silently.
  - **The node a `\node ... edge` path starts from.**
  - **Both ends on one node.**
  - **Locked edges.**
- **"Change start anchor" and "Change end anchor"** in the edge's context menu (right-click on the edge, a label or an end; the menu key or Shift+F10 when it is selected). Each opens a 3×3 compass of the node's anchors, with the border ("automatic") in the middle and the current one marked. The arrow keys move through the menu, and Escape closes it. Later steps add their items to the same menu.
- **Drawing a new edge.** The node under the pointer shows four connection handles just outside its sides. Dragging one to another node writes a new statement in the form the picture uses most (`edgeHead`, D34), after its last path and after both nodes (`planConnect`):
  - dropped on the node's middle: `\draw[->] (a) -- (b);`;
  - dropped on an anchor dot: `\draw[->] (a.east) -- (b.north);`, both ends with their anchors.

  An unnamed node gets a name in the same edit (D44). The new edge is selected.
- **Edge ids after an edit** follow the path through the changes (D46), so the edge stays selected after its end moves.

**Why:** Anchors are what keeps an edge attached in TikZ: an end written as a node name moves with the node, with no extra code. Dropping on a node's middle gives the plainest code, `(a) -- (b)`, which is what most hand-written flowcharts use. An anchor is written only when it was asked for.

## D50: Corners, Straighten, splitting a \draw, and moving an edge below a node (M2b step 4, 2026-10-07)
**Decision:**
- **The edit core takes edits that add or remove points** (`editPath` in `src/edit/edges.ts`). An edit says where each old point goes (or that it goes), how many points and segments the path has after it, and where new points must land. Points it leaves alone must stay exactly where they were; relative points after an edited one are held as before (D47). `writeStops` is now a case of it.
- **Corners** (`src/edit/vertices.ts`):
  - **Ghost handles** sit in the middle of each straight segment of the selected edge (not on segments shorter than 24 px on screen). Dragging one adds a corner there, shown live and snapped like a waypoint (D47). "Add vertex here" in the menu does the same at the point clicked.
  - **The new point** is written in emitter order (D47): a perpendicular coordinate when it lines up with two nodes, else `++(…)` from the point before it, else plain coordinates; plain numbers when the points around it are plain (TikZiT-style files). It is inserted before the segment's end, `(a) -- node {x} ++(2cm,5mm) -- (b)`, so the segment's labels stay on its first half; if they are nearer the end, it goes after the start instead.
  - **Corner handles** are small diamonds. Dragging one moves it (`planWaypoint`); double-clicking it, or "Remove vertex", removes the point and the operation after it: `(a) -- (1,1) -- (b)` becomes `(a) -- (b)`. Labels and other nodes stay in the code. A corner next to a curve keeps the curve's operation.
  - **Corners only go on straight segments.** Curved segments must be straightened first; orthogonal edges slide their segments instead (step 5). `edge` operations join their two ends directly and can't have corners.
- **Straighten** goes back to a plain `--` (D45): the edge's corners and curve go, its labels, comments and both ends stay. `to[out=90, in=180, red]` keeps its other keys, `to[red]`. On an `edge` operation, only the curve keys are removed from its options.
- **Rewriting the code between two ends** (`rewriteMiddle`) is shared with the orthogonal and curved modes: labels are kept (each after the step it belongs to), `%` comments are kept before the end's code, and the spacing around the operations is kept. It refuses code it can't safely rewrite: options in the middle of a path (they apply to all of it), an `edge` operation in the middle, or code it doesn't understand.
- **Split into separate edges** (`src/edit/split.ts`, D49) is in the menu of any `\draw` with more than one edge. Each edge becomes its own statement, with the statement's options; a shared end is written again; nodes right after an end stay with the edge that ends there. **Arrow tips:** TikZ puts them on the last subpath, so each piece gets the tips it drew before. An arrow key written in the statement is rewritten per piece (`<->` becomes `<-` on the first piece and `->` on the last, `-` in between); tips from a style are turned off with `-` on pieces that lose them. A piece that would need only one of two tips coming from a style is refused. The split is checked: every edge must draw the same segments, tips, labels, colour and line as before.
- **An end dropped on a node defined later** (D49) moves the edge's statement right below that node (after the top-level item holding it), with its comment, and then attaches the end. Refused, with the reason, for a statement inside a scope, a `\node ... edge` statement, or one that defines a name other code uses. The move alone must draw the same picture. One undo step; the status bar says the code was moved.
- **Refusal messages for shared ends** point to "Split into separate edges".
- **Menu order:** Add vertex here, Remove vertex, Straighten, (step 5–6 items), Change start/end anchor, Split into separate edges. Disabled items say why in their tooltip. Escape closes the menu even before it takes the focus.
- **Fixed:** an edge or path stayed selected after an edit by its old position in the text, because `mapPathId`'s pattern had lost its backslash (`d+`), so edits before it lost the selection.

**Interpreter fix (found while preparing step 6).** For `bend left` and `relative`, TikZ measures the control points' angles from the line between the two border points, not between the centres (`\tikz@to@compute@relative` in `tikzlibrarytopaths`). Bends were up to 0.6 pt off pdfTeX; the new probe `spike/engines/probes/p5-curves.tex` puts 12 curve points within 0.1 pt. The interpreter now also reads `out looseness`, `in looseness`, `relative` and `bend angle`, and `bend left=40` sets the bend angle for a later plain `bend left`, as in TikZ.

**Why:** Corners written relative to their neighbours follow the nodes when they move. Keeping labels, comments and spacing through every rewrite follows the project's rule that only the bytes an edit is about change. Splitting and moving statements are checked by drawing the result, so a case the rules miss is refused rather than misedited.

## D51: Orthogonal mode (M2b step 5, 2026-10-08)
**Decision:** `src/edit/orthogonal.ts`.
- **An orthogonal edge is a run of horizontal and vertical pieces** (`orthoPolyline`): its ends (a node's centre for a bare name), its written corners, and the corners `|-` and `-|` leave unwritten. Pieces of no length go and pieces in line merge. Edges with a diagonal or curved piece aren't orthogonal.
- **A run is written as a chain:** corners in pairs from the end, `-|` or `|-`, so the last operation always arrives at the end with a corner; with an odd number of pieces the first is a lone `--`. `(a) -- ++(0,-6mm) -| (b)`. Written corners follow the emitter order (D47): a perpendicular coordinate when one lines up with two nodes, else `++(…)` from the point written before it (rounded to whole millimetres, in the picture's own style: `++(0,-1.5)` where the picture writes plain numbers), else plain numbers in plain pictures. A `-|` corner needs no exact point, so rounding never bends the route.
- **The way each piece runs is kept as data,** not read back from the points, because an end at a border angle can sit a fraction off the line it was slid to.
- **Make orthogonal** (D45): a single corner where it can. `-|` and `|-` are both tried; the one that passes through no other node wins, then the one whose first piece runs the way the ends are further apart, and the way any anchor on a side faces (`(a.south)` leaves downwards). When both single corners cross a node, two corners through the middle: `(a) -- ++(2cm,0) |- (b)`. Ends that already line up get a plain `--`. Labels go after the piece they are nearest. Refused for `edge` operations (they join their ends directly) and edges that already run straight across or down.
- **Sliding a segment.** The selected orthogonal edge shows a small bar on each piece (pieces shorter than 16 px on screen get none). Dragging one slides it across, snapped to the centre lines and sides of nodes and to the edge's other pieces (Alt: no snapping), with the edge redrawn live. One undo step.
  - **A middle piece** takes both its corners along; corners that end up in line with their neighbours go, so sliding onto the end node's line leaves `(a) |- (b)`.
  - **A piece at an end** moves where the edge meets the node while it stays within the node's side: on a straight part of the side `([yshift=2mm]a.east)`, or `(a.east |- c)` when it lines up with another node; on a curved border (diamond, ellipse, the round end of a `rounded rectangle`) a border angle, `(a.34)`; back on the centre line, the bare name `(a)` again. Beyond the side, a short piece out of the node is added: `(a) -- ++(0,1cm) -| (b)`. A shared end isn't rewritten (it would move the other edge); the refusal points to Split (D49).
  - `rounded corners` doesn't change a rectangle's border in PGF (anchors and path clipping use sharp corners), so a terminal's side counts as straight, as TikZ draws it.
- **The interpreter keeps a shifted anchor's node:** `([yshift=2mm]a.east)` is an end on `a` (it moves with `a`), not a free point, though the path isn't clipped there. No corpus edge changed.
- **Menu:** "Make orthogonal" after Straighten; disabled with the reason when it doesn't apply. Orthogonal edges show segment bars instead of corner and ghost handles.

**Why:** `|-` and `-|` are how people write flowchart connectors, and a corner they compute themselves stays square when either node moves. Moving the end along the node's side, instead of adding a stub inside the node, is what a slid connector is expected to do in diagram tools.

## D52: Curved mode (M2b step 6, 2026-10-08)
**Decision:** `src/edit/curves.ts`.
- **Make curved** writes a plain `bend left` (D45): `(a) -- (b)` becomes `(a) to[bend left] (b)`. Corners go; labels, comments, ends and the `to`'s other keys stay (`to[red]` becomes `to[red, bend left]`). An `edge` operation gets the key in its own options, `edge[bend left]`.
- **Control handles.** Each curve of the selected edge shows its two control points, on dashed arms from where the curve leaves and arrives. Dragging one redraws the curve live; one undo step.
- **What a drag writes,** the first that draws it (SPEC.md's order):
  1. **`bend left=40`** (or `bend right`, plain `bend left` for 30°, `looseness=1.5` when it isn't 1). A curve written with `bend` stays symmetric while dragged: the other control point mirrors the one under the pointer. Bend angles are rounded to 5°.
  2. **`out=60, in=180`**, with `looseness` when both ends agree, or `out looseness` and `in looseness` when they don't. Hold **Alt** to drag one end of a bend on its own, which writes this form. Angles are whole degrees, loosenesses tenths.
  3. **`.. controls +(…) and +(…) ..`** is kept for curves already written that way: the dragged point is rewritten relative to its end (plain numbers stay plain).

  A free curve dragged close enough to symmetric becomes a `bend` again. Each result is checked by laying it out: the control point must land within rounding of where it was dropped.
- **The interpreter, checked against pdfTeX** (probe `p5-curves.tex`, D50): for `bend` and `relative`, TikZ turns the angles by the line between the centres to find where the curve meets the borders, then measures the control points from the line between those border points (`\tikz@to@compute@relative`). Without `relative`, the angles are absolute and the curve leaves from the angle anchor. Control distance is 0.3915 times the distance between the two border points, times the looseness of that end.
- **Menu:** "Make curved" after "Make orthogonal". Straighten (D50) undoes either. The panel's hint says what can be dragged for each form.
- **Fidelity:** `npm run fidelity` gives 235 of 331 nodes within 1 pt of pdfTeX: the M2a count (204) plus the 31 new probe points. No corpus node changed.

**Why:** `bend left` and `out`/`in` are what people write for curved connectors; `.. controls ..` is for curves drawn by hand, so it's kept rather than introduced. Keeping a bend symmetric while dragging keeps it a one-key edit, and Alt is already "free" elsewhere (no snapping).

## D53: Owner's answers on 2b steps 4–6, and the curve handles (2026-10-08)
**Decision:** The owner tested steps 4–6 by hand (corners, Make orthogonal with sliding, Make curved with its control point) and answered the report's four questions:
1. **5° bend snapping: approved.** Out and in angles stay whole degrees.
2. **Alt never frees a bend.** Alt means "no snapping" everywhere. Curves get handles instead (done in this entry's code, `src/edit/curves.ts`, `planCurve`):
   - **A handle near each end** (on the arm that leaves the end, a short way along it). Dragging it changes only that end's angle and writes `out=` or `in=`: edited in place when the curve is already written that way (`to[out=90, in=180]` becomes `to[out=60, in=180]`), else the curve is written as `out`/`in` with the loosenesses it had (a bend turns into `out`/`in`, other keys stay). The angle is the direction from the node's centre (or the point) to the pointer, in whole degrees; it snaps to multiples of 15° within 3° unless Alt is held.
   - **A handle in the middle of the curve** keeps it symmetric. A bend stays a bend: the pointer sets how far the middle is from the chord, which sets the angle (rounded to 5°, or 1° with Alt) at the looseness the curve already has; `looseness` is only raised when even 85° falls short. A curve written with `out`/`in` keeps its angles and both loosenesses are scaled together. The pointer's movement along the chord is ignored, so a drag gives `bend left=45`, not `bend left=39, looseness=1.1`.
   - **`.. controls ..` curves** keep their two control points as handles (they have no end or middle handle).
3. **Shifted anchors such as `([yshift=2mm]a.east)`: approved** for sliding an end segment along a node (D51).
4. **`edge` operations:** when the user explicitly chooses Make orthogonal or adds a corner, `(a) edge (b)` is converted to `--` (moving it into its own `\draw` if needed), verified by re-layout, in one undo step. (Implemented: `src/edit/edgeop.ts`, used by Make orthogonal and Add vertex; the menu and the ghost handles offer them for `edge` operations. The conversion is checked by laying the result out again: every other path, the node positions and the edge's look must be unchanged, with `every edge` styling written out when the edge only had it from there. It is refused for relative ends, for statements other than `\draw` and `\path` (such as `\fill`), and for a `\node ... edge` start. `composeChanges` no longer uses CodeMirror's ChangeSet, which counts a CRLF line break as one character.)
5. **Split:** `[-]` is written only to override an arrow tip inherited from a style or the picture's options. Otherwise it is omitted (`\draw (a) -- (b);`). (Implemented: `planSplit`.)

**Why:** Alt already means "no snapping" in every other drag; giving it a second meaning for curves would have made the key unpredictable. Handles near the ends and in the middle are the controls other diagram tools use for curves. Keeping looseness fixed while the angle changes keeps the code readable: `bend left=45` rather than a drifting `looseness`.

## D54: Edge labels (M2b step 7, 2026-10-08)
**Decision:** `src/edit/labels.ts`.
- **Add label here** (edge menu) writes a label on the segment nearest the click, before that segment's end: `(a) -- node[pos=0.25, above] {text} (b)`. It is shown first with its text ready to type over, as a new node is (D41): nothing is written until Enter, Escape leaves the code as it was, and an empty label adds nothing. `pos` is written only when the click is not near the middle (quarters snap, otherwise twentieths). The side follows the edge: above or below a mostly level segment, left or right of a mostly upright one, on the side clicked. It works on lines, corners, orthogonal pieces, curves and `edge` operations. The result is checked by layout: no new errors, no node moved, no path drawn differently, exactly one new label, on the same edge.
- **Sliding a label.** Dragging a label of an edge writes `pos=`: the point the label is attached to follows the pointer's movement and is projected onto the label's own segment (a line, an orthogonal piece, or a curve by its parameter, as TikZ's `pos` counts it). Positions snap to quarters, then round to twentieths; Alt rounds to hundredths. A `pos=` already there is edited in place; `midway`, `near start` and the like are replaced by `pos=`; with none, `pos=` is added to the label's options (a label with no options gets `[pos=…]`). A label whose position comes from a style key gets `pos=` after it, which wins. The result is checked: the label must land within 0.01 of the position written and nothing else may change. One undo step.
- **The layout records where a path label is attached** (`pathPos`: its `pos` and the point on the path).
- **Yes/No on decisions** (D45). A decision is a diamond or a node styled `decision`. A new edge out of one (Tab, Enter, drawing an edge from it) gets `node[near start, right] {Yes}` for the first branch and `{No}` for the second: `right` of an upright edge, `above` a level one. If the figure already writes branch labels, the pair follows it (`yes`/`no`, `Ja`/`Nein`, `Y`/`N`, `True`/`False`); with any other wording on its decisions' branches, an unlabelled first branch, or two branches already, nothing is added. The status bar and notes say when a label was added.

**Why:** Labels are nodes inside the path, so adding and sliding them are small insertions or one-option edits that leave everything else alone. Writing the label only when applied matches node creation, so Escape stays clean.

## D55: The edge properties panel (M2b step 8, 2026-10-08)
**Decision:** `src/edit/edgeprops.ts`, `src/ui/edgepanel.tsx`.
- **What it edits:** arrow direction (none, end, start, both) and tip (the figure's default, or `Stealth`, `Latex`, `To`, `Triangle` from arrows.meta, which is loaded if missing); solid, dashed or dotted; colour; and the named line widths (`thin` is TikZ's default). The colour picker is the node panel's (D37) and offers "Default" to drop the edge's own colour.
- **Scope, as for nodes:** "This edge" (or "This path" when the `\draw` has several edges), or "All *flow* edges (N)" for each document style the edge's options name directly. A style edit changes the style's `\tikzset` body in place; the status bar says how many other edges change with it. An `edge` operation's properties go in its own `edge[…]` options.
- **How an item is written:** the last item of the group (`dashed`, `densely dotted`, …) is replaced in place and earlier ones removed; with none, the new item is appended to the options after the command, or a list is added (`\draw[->]`). The form the edge already uses is kept: a bare `red` stays bare, `draw=red` stays `draw=`. Returning to a value the edge inherits removes its own item instead of repeating it: `solid` is written only to override a style's dashes. An arrow is written as `->`, `<-`, `<->`, `-Stealth`, `Latex-Latex`; `-` is never written.
- **Checked by layout:** no new errors, no node moved, nothing added or lost, and the edge must come out as asked (its dash, width, colour or tip count). A later key that overrides the edit makes it refuse, with the reason.
- **Refused:** arrow tips of one edge of a path with several edges (they belong to the path; Split first), locked edges, styles the editor can't change, and `#1` style arguments.
- **Reading:** the panel shows what the edge gets from its options and styles, and which style it comes from.

**Why:** The same scope idea as the node panel (D37), so a figure that styles edges through a named style (`\draw[flow]`) is edited at the style, and a hand-written `\draw[->, thick]` is edited in place.

## D56: Delete (M2b step 9, 2026-10-08)
**Decision:** `src/edit/delete.ts`. The Delete key (or Backspace) on the canvas, a button in the panel and "Delete edge" in the edge menu remove the selected nodes, edge or path as one undo step. The selection is cleared.
- **Nodes** (several may be selected). In this order, each step re-drawing the picture:
  1. **Nodes placed relative to a deleted node** (`below=of b`, `at (b |- a)`, `at (b.south)`, a `\coordinate` at it) are written again against nodes that stay, where they are now: the move planner (D24) with the deleted names excluded, so `below=of b` becomes `below=26mm of a` or `at (a |- c)`, and when nothing else fits they get plain coordinates ("pinned at its current position"). The status bar lists what was re-attached.
  2. **Corners of edges that stay**, written relative to a deleted node (`(b |- d)`), are written another way (relative to the point before, or plain), by the waypoint writer (D47) with the names excluded.
  3. **Edges that would be left dangling are deleted**: every edge that starts or ends at a deleted node. An edge in a `\draw` with several edges is split out first, and an `edge` operation becomes a `--` of its own first (D49, D53), so only that edge goes. A path that starts in a deleted node's own `\node … edge …;` statement goes with it.
  4. **The node statements** are removed: the whole line, and a comment after the statement on that line, when it is alone there; otherwise only the statement.
- **An edge:** the same, for one edge. **A path** that isn't an edge (a circle, a `\path` with only labels) is removed as a statement.
- **Checked by drawing the result:** no new syntax errors, every other node within 1.5 mm of where it was, no name that LaTeX would reject that wasn't already rejected, and every other edge still joining the same nodes. Anything else refuses, with the reason, and the code stays as it was.
- **Refused, with the reason:** a name used in code the editor keeps as written (a loop, a matrix, a pic); a node in the `fit` of another one (take it out of the fit first); a node written inside a path (`… coordinate (m)`); a node that is part of a chain or placed in a way that can't be rewritten without moving it; an edge kept as written (shapes, code it doesn't understand).
- **Not done:** libraries and styles that nothing uses any more are left alone (D34's conservative rule); labels of a deleted edge go with it.

**Why:** "Never leave code LaTeX can't compile" (D36) extends to removal. Moving dependents to where they were, not leaving them to jump, is what someone deleting a box in the middle of a flow expects, and the exclusion approach reuses the planner that already knows how to write a position readably.

## D63: Form changes put overlapping labels beside the line (M3 step 4, 2026-10-08)

## D66: Our driver and our own DVI-to-SVG converter (M3 step 6, 2026-10-09)
**Decision:**
1. **The driver** is `engine/build/texinputs/pgfsys-tikzflow.def`. It loads pgf's `pgfsys-dvisvgm.def` unchanged and replaces four definitions (pgf is LPPL and/or GPL; the file takes GPL-3.0-or-later):
   - no "box mode" for text: a colour change in a node's text sets the stroke as well as the fill, and scopes in TeX boxes no longer add `stroke="none"` (this is what lost `\matrix` cell borders and strokes of pictures nested in node text, D15 item 3);
   - `\pgfsys@hbox` and `\pgfsys@hboxsynced` without `stroke="none"`;
   - a picture starts with `\special{color push tikzflow inherit}` instead of `gray 0` (item 3 below);
   - the outermost picture writes `\special{tikzflow:picture minx miny width height}` at its box's lower left corner, so the app can put TikZ's origin exactly over the native canvas.
   The format is dumped with the class option `dvisvgm`, so graphics, xcolor and expl3 load their dvisvgm back ends (`l3backend-dvisvgm.def`, settling D59's open point). pgfsys.sty turns that option into `pgfsys-dvisvgm.def`, so a LaTeX file hook (`file/pgfsys.code.tex/before`) sets our driver again, and the dump fails if pgf loaded another.
2. **The converter is ours, not an adapted dvi2html.** `src/engine/dvisvg.ts` reads the DVI and follows dvisvgm's rules for its specials (`raw`, `rawdef`, `rawset`/`rawput`, `{?x}`, `{?y}`, `{?nl}`, colour push/pop); `src/engine/tfm.ts` gives exact advances with TeX's own scaling arithmetic; characters are drawn as paths from the Type 1 outlines (`src/engine/type1.ts`), defined once each with `stroke="none"`. Output is in bp with an exact `width`/`height` in pt, so no 72/72.27 correction is needed (D15 item 6). **This departs from the plan's "dvi2html adapted"; the owner may still prefer adapting dvi2html.** Reasons: only a minified dvi2html was at hand (its source would have been one more download), it is built on Node stream and Buffer polyfills, it is written for the ximera driver's specials, and it draws text with BaKoMa web fonts, whose licence the M5 audit would have to clear and which an exported SVG/PNG/PDF (step 11) would have to embed. Paths from the AMS Type 1 fonts (OFL-1.1, already in the M0 package set) make the SVG self-contained. The converter and the font readers are about 800 lines; dvi2html is no longer used anywhere in the app.
3. **Colour of text.** dvisvgm writes black text with no fill, so it takes the colour of the SVG group around it. pgf relies on that inside pictures, but the second part of a `rectangle split` is coloured with a colour special (`gray 0`) and so took the node's fill colour and vanished. With our driver's `inherit` marker, the converter writes every colour a special sets, black included, on the text, and only `inherit` takes the group's colour.
4. **Fonts** come from CI (`engine/build/fonts.ts`): for every TFM of Computer Modern, the AMS fonts and LaTeX's own fonts (188), `fonts/<name>.json` holds its metrics and its outlines by character code (178 have outlines; the 10 without are dummies and `icm*` fonts). 3.2 MB gzipped in all, about 19 kB per font, fetched when a page uses the font.
5. **Checks.** CI compiles the 13 comparison diagrams with our engine and converts each DVI with the real dvisvgm (`engine/build/references.ts`). `npm run dvicheck` rasterises ours and dvisvgm's in Edge: 0% difference on 12 diagrams; on the 13th, dvisvgm's fraction bar inherits a stroke and is drawn thicker (ours, like pdfTeX, isn't). Against pdfTeX (busytex, `npm run compare-engines`): 0–1.9% on all 13, the rest being antialiasing of glyph edges and the 0.1pt hairline (which pdf.js draws a pixel wide); `\matrix` cell borders and nested pictures, TikZJax's two defects, are 0% and 0.4%.

**Why:** The owner's D15 requirements for the driver (known licence, strokes kept in boxes, bp units). Doing the conversion ourselves made every one of them a few lines, and gives exports self-contained SVG.

## D67: The engine worker, its files and the release (M3 step 7, 2026-10-09)
**Decision:**
- **The runtime** (`src/engine/texlib.ts`) is our TypeScript version of web2js's `library.js` (GPL-3.0, via TikZJax's browser copy): the 19 imports tex.wasm needs. A file TeX can't find is missing, whatever its name; `\filesize` gives -1 for it (D59); files are bytes; a file not yet fetched pauses TeX with asyncify and resumes it with the answer. TeX's memory (164 MB) is allocated once per worker and reset from `core.dump` for each compile; fetched files stay cached for the session.
- **The worker** (`src/engine/worker.ts`) loads `index.json`, then `tex.wasm.gz` and `core.dump.gz` (inflated with `DecompressionStream`, or taken as they are if a server already inflated them, D12), compiles one input at a time, converts the DVI and reads the log. Files not in the index are missing without a request. `src/engine/client.ts` runs one compile at a time and drops a waiting one when a newer one is asked for.
- **The input** (`src/engine/input.ts`) continues the format's preamble: `\scrollmode`, the user's preamble copied verbatim from the line after `\documentclass` (with `\usepackage` of packages the engine lacks, and of font packages, taken out on the same lines: D15 item 5, D16), font sizes for the `11pt`/`12pt` class options, sans serif for beamer, the definitions the parser found before the picture, and the picture, with each locked block between `tikzflow:begin`/`end` specials on the same lines. Every copied piece records where it came from, so TeX's `l.<n>` maps back to the user's line. The document's other text isn't compiled.
- **The log** (`src/engine/log.ts`) gives each error's message, line and the file TeX was reading (from the `(file` and `)` it prints; the 2026 kernel quotes names).
- **The files** (`engine/build/packages.txt`, `packages.ts`, `pack.ts`): 44 TeX Live packages, resolved by name with kpsewhich (pgf with every library, pgfplots, tikz-cd, tcolorbox, amsmath and amsfonts, mathtools, siunitx, the tools bundle, booktabs, …): 979 files, 3.6 MB gzipped, plus the fonts. The folder the app serves is `engine/<tag>/` with `index.json`; CI packs it as one `engine.tar` (10.8 MB) for the release. A tag `engine-*` publishes it as a GitHub prerelease; `engine/release.json` pins the tag and the tar's SHA-256; `npm run fetch-engines -- engine` downloads it, checks the hash and unpacks it into `vendor/engine/<tag>/`. The dev server serves that folder as `/engine/<tag>/` byte for byte; the build copies it into `dist/` (1,234 files, 15 MB, the largest 2.98 MB). `public/_headers` caches `/engine/*` for good (the tag is in the path).
- **Reproducible format.** The dump's clock is the commit's time (`SOURCE_DATE_EPOCH`). The release run of `engine-2026-10-09` and the branch run of the same commit gave the same `core.dump` SHA-256 (`18af1566…`); D59's open point is settled. (`engine.tar` differs only in `index.json`'s version string.)
- **No cross-origin isolation needed:** the engine uses no SharedArrayBuffer, so production sets no COOP/COEP.
- `scripts/stage-engine-ci.ts` now unpacks a CI run's `engine.tar` into `vendor/engine/ci-<run id>/`, for `?engine=ci-<run id>` on the app and the comparison pages. The M3 step 1 path through TikZJax's worker (`?build=ci`) is gone.

**Why:** D15 items 2, 4, 5 and the step 7 plan. Pinning by hash means the files the app serves are exactly the ones CI built and the hash records.

**Decision:**

## D71: The page: an imported preamble and a column-width guide (M3 step 10, 2026-10-09)
**Decision:**
- **The imported preamble.** The toolbar's **Page** button opens a panel where the user pastes the preamble of their paper (or the whole file: it is cut at `\begin{document}`, and its `\documentclass` line, which the engine's `standalone` format can't take, is read for the font size and for Beamer). It is kept in this browser (localStorage), not in the code pane. The TeX preview compiles it in front of a bare picture with the same treatment as a preamble in the code (`usePreamble` in `src/engine/input.ts`: unusable packages out, 11/12pt sizes, the notes for left-out and font packages). **When the code has a preamble of its own, that one is used and the imported one is ignored**, and the panel says so. Errors in it are placed by line: "In the imported preamble, line n" (`LineSegment.in`, `locate`).
- **Its limits, said in the panel.** Styles and macros defined only in the imported preamble are used by the TeX preview but not by the quick preview or the editing tools: the editing model (`analyzeDocument(text)`, called from every planner) sees only the code, and passing a second source through all of them would make every edit check depend on it. Fonts stay Computer Modern (D16).
- **Page widths** (`src/tikz/page.ts`, pure, 16 tests). The engine has no page (the format is `standalone`), so they are worked out the way TeX would: the class's defaults for `article`, `report` and `book` (size10/11/12.clo's 345, 360 and 390 pt, or what the paper leaves to whole points, two columns 10 pt apart), Beamer (the slide less 1 cm each side: 307.29 pt at 4:3, 398.34 pt at 16:9, matching the values Beamer itself gives), the geometry package (margins, `hmargin`, `textwidth`, `text`, `total`, `scale`, paper names), and `\setlength`, `\addtolength` and `\textwidth=…`, in order, with multiples of other lengths. Adding a class is a few lines.
- **The guide.** Two dashed lines one `\columnwidth` (or `\textwidth`, or a typed width) apart, centred on the figure, since that is where a centred figure lands; a dimension line and label at the bottom of the view; red, with "the figure is N mm too wide", when the native layout's box is wider. The panel says whether the figure fits. It follows the code's preamble automatically for a full document. Settings are per viewer.
- **The TeX preview uses the same widths.** The format's class is `standalone`, which has no page, so after `\begin{document}` (which sets `\columnwidth` again; found by testing) the input sets `\textwidth`, `\columnwidth` and `\linewidth` from the widths worked out above, for the code's own preamble or the imported one, and not for a class whose widths are unknown. A node with `text width=\columnwidth` is then a column wide in the TeX preview (checked in `test/engine-run.test.ts`).
- **Not done:** the quick preview still reads `\textwidth`, `\columnwidth` and `\linewidth` in lengths of the picture (`text width=0.5\textwidth`) as 345 pt (`KNOWN_LENGTHS` in `src/tikz/units.ts`), so it can differ from the TeX preview for such a picture; fixing it means threading the page through the interpreter. To decide with the owner.

**Why:** SPEC Milestone 3: "Optionally import a user's preamble (macros, fonts, `\textwidth`), with a guide showing column width."

## D74: Save and open, and share links (M3 steps 12 and 13, 2026-10-09)
**Decision:**
- **Autosave** (`src/ui/files.ts`): the work is kept in IndexedDB (database `tikzflow`, one small key-value store) half a second after the last change and when the page is hidden or closed: the text, the text as last opened or saved, the file name, its encoding and the picture shown. The editor starts with it (`restoreOnStart` runs before the app renders, so the first document is the kept one, with no undo step back to the sample); a first visit shows the sample. If IndexedDB is refused (a private window) the app works and simply doesn't remember. The engine-less parts of the page settings (imported preamble, typed widths, presets) stay in localStorage as before.
- **Open and Save in place** (File System Access API, Chromium): **Open…** uses `showOpenFilePicker` and keeps the file's handle, **Save** (Ctrl+S, in the code pane too) writes back to it (a handle kept from an earlier visit asks for permission again; the click is the gesture it needs), **Save as…** uses `showSaveFilePicker`. The handle is stored in IndexedDB so Save still works after a reload. A `●` after the file name says the code differs from the file as last opened or saved; the work is in the browser either way. Encodings are kept (D29): a character the file's encoding can't hold is saved as UTF-8, and the status bar says so.
- **Everywhere else** (Firefox, Safari): **Open…** is a file chooser, **Save** is a download of the file under its own name, and there is no Save as… button. **Download** stays in every browser. Dropping a file on the page still opens it.
- **Work is put aside, not replaced:** opening a file or a share link while other work is on screen keeps that work as "previous" (IndexedDB); **Restore previous work** in the toolbar brings it back (and puts the current work aside in turn). The sample and empty text are not kept.
- **Share links** (`src/ui/share.ts`, `src/ui/sharepanel.tsx`): the toolbar's **Share** gives a link whose fragment carries the code: `#tf1=<base64url of the deflate-raw of the UTF-8 text>` and `&p=<n>` for a picture other than the first. Compression is the browser's `CompressionStream`; there is no server and a fragment is never sent to one, so nothing is uploaded or stored. The link holds the code only: not the imported preamble, typed widths or other settings. The panel says that, shows the length, and warns past 8,000 characters (some chat and mail programs cut long links). A real figure of 10 kB gives a link of about 3 kB.
- **Opening a link:** at start, or when a link is pasted into a page that is already open (`hashchange`), the code replaces what is on screen, the previous work is kept as above, and the fragment is taken off the address (so a reload doesn't reopen the link over later work). A damaged link (cut short, not valid) says so in the status bar and changes nothing.
- **Tests:** `test/share.test.ts` (round trips, damaged links), `test/e2e/files.spec.ts` (6: restore after a reload, Open/Save/Save as with fake pickers, the download fallback without them, work put aside and restored, a link opened in another browser context, a damaged link). The end-to-end specs now import `test` from `test/e2e/base.ts`, which waits for the code pane after `goto` and `reload`, since the app starts once the kept work has been read.

**Why:** SPEC Milestone 3: "Save and open: autosave to IndexedDB, the File System Access API in Chromium browsers, and a download/upload fallback elsewhere" and "Shareable links: compress the source into the URL hash. There is no server."

## D78: Dragging a multi-selection, or a fit node, as a group (M4 step 1, 2026-10-10)
**Decision:**
- **Starting a group drag.** With two or more nodes selected (Shift-click), dragging any of them drags them all. Dragging a `fit` node drags the nodes it fits (recursively through nested fit nodes), and the fit node follows. A click on a node of the selection without dragging selects just that node, as before. Snapping works on the node under the pointer; the other members and everything that follows them are not snap targets. Alt drags without snapping.
- **What is rewritten** (`src/edit/group.ts`, `planGroupMove`). Only members placed against something outside the group are rewritten, in code order, each through the single-node emitter (D24), so the same relational forms come out and each member may refer to members written before it. A member placed against another member follows it without any edit (`\node[below=of b] (c)` stays byte for byte). A member that only partly follows (`at (a |- x)` with `x` outside) is rewritten in a second round.
- **A translation keeps each member's own form.** Members that were lined up before the move still are, which the user didn't choose now, so a member isn't newly related to another member. A plain-coordinate picture keeps its numbers (D24). A node at a calc expression keeps it and gets `xshift`/`yshift`. A node with `shift=(...)` keeps that item and gets `xshift`/`yshift` beside it, since TikZ adds them up (this also applies to single drags now).
- **Edges.** Corners written as plain numbers, on an edge whose two ends both move by exactly the group's shift, move along (`(a) -- (1,-2) -- (b)`). Relative (`++`) and perpendicular corners follow by themselves. Edges to nodes outside the group are left alone, as with a single drag.
- **What may not move.** A member that is locked (other than by an undefined name, which is pinned where it lands, as with a single drag) refuses the whole drag, with its name and reason. Nothing is half-moved.
- **The check.** After writing, the picture is laid out again: every member lands the group's shift away (each rewritten one rounded to whole millimetres), and every node that is neither a member nor follows one stays exactly where it was. "Follows" includes nodes placed on a path that runs from or to a moving node (edge labels, `coordinate[midway]`) and what is placed against those: `dependents()` alone missed them (found on `se-421789-complicated-fit.tex`).
- **One undo step,** like every drag (D25).
- **Two emitter fixes found by the group goldens.**
  - A diagonal relation with a distance that rounds to nothing (`below right=1.3cm and 0pt of a`) is never written. The straight relation with a shift (`below=1.3cm of a, xshift=5mm`) is offered instead, even past the overlap that otherwise switches to a diagonal.
  - tikz-ext's corner placements (`east above=of a`, `north left=of a` and the other six) set a node's position. The interpreter didn't know them and treated such nodes as placed at the origin and movable, so a move added an `at` that TikZ ignores. They are now "a position the editor doesn't understand": the node is locked with that explanation.
- **Tests:** `test/group.test.ts` (12), `test/golden-group.test.ts` (34 golden files in `test/fixtures/golden/group/`: two neighbouring editable nodes moved by (5 mm, −3 mm) and the first fit node dragged by (−4 mm, 4 mm) on every corpus picture; changes only in the members' statements, corners of paths and a positioning library), `test/e2e/group.spec.ts` (3).

**Why:** SPEC Milestone 4, "Drag a multi-selection as a group" (added with D34). Rewriting only what isn't carried along keeps the diff minimal and keeps the relations the author wrote inside the group.

## D79: Chain nodes made draggable by writing the chain out (M4 step 2, 2026-10-10)
**Decision:**
- **What the chain does, checked against pdfTeX first** (`spike/engines/probes/p8-chains-explicit.tex`, `npm run fidelity`). In pgf's chains library, `on chain` places the node when the key runs (`below=of chain-2`, with the `node distance` and `on grid` of that moment), so a position written **after** `on chain` wins and one written **before** it is replaced; an `at` clause comes after all options and wins. Every node on a chain, named or not, also gets the aliases `chain-<n>`, `chain-end` and (the first) `chain-begin`, and `\chainin` gives the node it chains in the next number. The interpreter had three of these wrong: a position written before `on chain` won, named chain nodes had no `chain-<n>` alias, and `\chainin` didn't count. All three are fixed. A node on a chain is now locked only when the chain actually places it, so nodes like `\node[proc, right=of p1]` (with `on chain` inside the `proc` style) are editable as written. On the corpus, no node's position changed (full `npm run fidelity`), and the probe matches pdfTeX exactly (7 of 7).
- **Converting (D77 item 4).** Dragging a node its chain places writes out the position of **every** node that chain places, then moves the dragged node, as one edit and one undo step (`src/edit/chains.ts`, `planChainMove`). The position is appended **after** `on chain` in the node's last option list: `\node[draw, on chain, join, below=of a] (b) {B};`. `on chain` and `join` stay, so the nodes stay on the chain: the joins are still drawn, `chain-<n>` names still work, `\chainin` still works, and nodes added to the chain later still follow it. Converting only adds bytes: nothing the author wrote is removed.
- **Exactness.** Writing a chain out must move nothing. Each node tries, in order: `below=of prev`; `below=<the chain's distance> of prev`; the same with the chain's grid setting first (`on grid=false, below=of prev`, needed when a style says `on chain, on grid`: the chain placed the node before `on grid` ran). The first that lands within 0.01 pt of where the chain put it is used. If none does, nothing is written and the drag is refused with that reason. Distances are written in millimetres when exact, else in points.
- **Names.** A node another chain node follows must be referred to by a written name. An unnamed one gets a name from its label, as Tab names an unnamed parent (D44): `\node[draw, on chain] (checkInput) {Check input};`. Its `chain-<n>` alias still works (pgf adds it to named nodes too). Label words now skip the arguments of `\rotatebox`, `\scalebox` and `\resizebox` that aren't text (`\rotatebox{90}{Identification}` gives `identification`, not `n90Identification`).
- **Group drags** with chain nodes in them write those chains out first, in the same edit (D78).
- **The summary** counts nodes a chain places as editable, since they can be dragged. The panel still explains, when one is selected, that dragging it writes the chain out.
- **Tests:** `test/chains.test.ts` (10), `test/golden-chains.test.ts` (golden files in `test/fixtures/golden/chains/`: the first node each chain places, dragged by (5 mm, −3 mm), in both chain pictures of the corpus; changes only in statements of nodes on that chain and a positioning library), `test/e2e/chains.spec.ts`. `se-382997-chains-indented.tex` now has editable nodes, so it has golden files in `test/golden.test.ts` and `test/golden-group.test.ts` too.

**Why:** SPEC Milestone 4, "Make chain nodes draggable by converting them to explicit positioning" (D31 item 4), with the owner's answer that the whole chain is converted (D77 item 4). Keeping `on chain` and `join` makes the conversion a pure addition that keeps everything the chain does except placing nodes, so it can't break a reference to `chain-3` or a `\chainin` elsewhere in the picture.

## D80: Auto-layout with elk.js, written back as relations (M4 step 3, 2026-10-10)
**Decision:**
- **elk.js 0.12.0, pinned exactly.** It is the first release licensed `EPL-2.0 OR GPL-3.0-or-later` (its `LICENSE.md` names GPL-3.0-or-later as a secondary licence in Exhibit A); 0.11.x and earlier are EPL-2.0 only, which can't be combined with our GPL-3.0 code, so the pin must not go below 0.12. It is loaded with a dynamic `import()` on the first auto-layout, so it is a chunk of its own (1.4 MB, 442 kB gzipped) that the main bundle doesn't carry; the service worker caches it with the app (D70), it contains no `eval` and runs under the CSP (D75), and its only URLs are EMF namespace names, never fetched.
- **ELK decides the structure, not the coordinates** (`src/edit/autolayout.ts`). The layered algorithm with: edges into one node merged (so nodes line up centre to centre), depth-first cycle breaking and the code's node and edge order (back edges are the ones that go back in the flow, and the result keeps the author's order where it can), Brandes–Köpf placement, one graph for all components, the gaps the picture's node distance gives (border to border; for `on grid` pictures what is left between the borders). Edges between full-size nodes get a higher straightness priority than edges to small nodes (under a quarter of the median area), so connector circles don't pull the main flow out of line. Sizes and gaps are rounded to 0.01 pt: ELK breaks ties on the last bit, and the same picture must always give the same layout. From ELK's result the planner reads layers (bands along the flow), the order within each layer and columns (nodes lined up across layers).
- **Each node is written as a relation to a node before it in the code** (positioning needs that), in code order. The first laid-out node stays where it is and keeps its code; the layout is built around it. For each node, the first of these that is clear of the nodes already placed:
  1. **its relation as written**, when it follows one node and still says what the layout says (same column in the next or previous layer, or next to it in the same layer); old-style `below of=` counts;
  2. `below=of` the node above it in its column (`above=of` the one below), at the node distance;
  3. `right=of` its neighbour in the layer (`left=of`), at the node distance, else at ELK's gap;
  4. `at (a |- b)`, in line with a node of its column and one of its layer;
  5. a straight relation with a distance to a node further along its column or layer;
  6. from the nearest placed node: a straight relation, a diagonal (`below right=1cm and 2cm of a`), or a straight one with a shift, to where ELK puts it, lined up with its column and layer; if that is not clear either, the nearest clear place, searched outwards in 5 mm steps.
  A relation that lands where the node's current one already puts it is kept as written. Three passes: each lines nodes up with where the previous pass put nodes defined later in the code (ignoring placements that went through the node itself, which would carry its own error back). Distances are whole millimetres (`formatDistance`), and the planner predicts each node's centre with the rounded distance.
- **A node's own `node distance` (and `on grid`) goes when its relation is rewritten**: it served the old relation (`right of=x, node distance=6cm`) and would otherwise stretch the new `below=of`. The relation is planned with the distance the node inherits. Nothing else in the node's options changes; `on chain` and `join` stay (D79).
- **Writing and checking.** All relations are written in one go and the result laid out: every node must land within 0.6 pt of where it was planned, else the nodes are written one at a time, each checked, with the general emitter (D24) for one whose relation doesn't land. Relations that would be written exactly as they are aren't changes. The positioning library is loaded if needed (D28). Nodes outside the layout must stay exactly where they were unless they follow a laid-out node (fit nodes, labels, nodes placed against one). One undo step.
- **Edges keep their form (D77 item 1).** Corners written as fixed coordinates (`(2,1)`, `(-3.5cm,1cm)`, `(30:2cm)`) on an edge whose ends moved are removed with the edge editor's Remove vertex, so `(a) -- (2,5) -- (b)` becomes `(a) -- (b)` and `(a) -| (3,2) |- (b)` becomes `(a) -| (b)`. Relative corners (`++(1,0)`), corners at nodes and perpendicular corners move with what they refer to and stay. A curve through fixed control points is left as written, with a note.
- **Two exceptions, each through the edge editor's own planners and named in the status bar.** A one-corner orthogonal edge between bare node names whose ends now line up (`(base) |- (stop)` with `stop` straight below `base`) has its corner inside a node, so TikZ would run the line to that node's centre: it is straightened to `--` (an orthogonal route between two nodes in line is a straight line). And a label that a moved line now cuts through, and didn't before, is put beside the line with `auto`/`auto, swap`, the rule form changes use (D63). This goes past D65, which leaves labels alone when a node is dragged and shows a marker instead: a drag is one deliberate move the user can adjust, while auto-layout moves everything at once and would leave markers all over the picture (11 labels on the corpus). **For the owner to confirm.**
- **Scope (D77 item 2).** The whole picture, or the selection when two or more nodes are selected (a fit node in it stands for what it fits). Nodes that stay: locked ones (other than chain nodes, whose chains are written out first, D79), fit nodes (they follow), coordinates. A laid-out node that ends up on a node that stays is reported in the status bar, not refused.
- **Direction.** Top to bottom or left to right, chosen in the panel; the one the picture mostly runs in now is marked "(as now)".
- **The panel** (`src/ui/layoutpanel.tsx`): the toolbar's **Layout** opens it; it says what will be laid out, which locked nodes stay, and that one Ctrl+Z undoes it. ELK runs asynchronously ("Laying out…"); if the code changes meanwhile nothing is written.
- **Not done:** reordering statements (a node defined early in the code but placed deep in the flow gets a long relation to an earlier node, `below=20cm of init`); edges that end on a fit node aren't in ELK's graph; anchors written on edge ends (`(a.east)`, `(b.240)`) stay as written, so pictures built from anchored edges can look worse after a layout.
- **Tests:** `test/autolayout.test.ts` (14), `test/golden-autolayout.test.ts` (every corpus picture in both directions: changes only in the laid-out statements, paths and a positioning library; no new syntax errors; laid-out nodes don't overlap; a second run changes nothing, except `se-382997-chains-indented.tex`, where writing the chain out adds `on grid=false` and so changes the gaps ELK is given; golden files in `test/fixtures/golden/autolayout/`), `test/e2e/autolayout.spec.ts` (2), one in `test/offline/` (offline, under the production CSP) and one in `test/live/`. `npm run autolayout:report [-- <filter>] [-- --right] [-- --full] [-- --out=<dir>]` prints what it writes for every corpus picture. `npm run layout:bench`: 0.9 s top to bottom on the 200-node, 250-edge picture, ELK's first load included.

**Why:** SPEC Milestone 4: "Auto-layout with elk.js using a layered algorithm. Results are written back as relative positioning, not coordinates." Reading only ELK's structure lets the result be the relations a person writes; ELK's own coordinates differ from TikZ's (its layers are bands, TikZ measures each relation border to border) and would come out as `below=13.4mm of a, xshift=2.1mm`.

## D81: The owner's answers on the M4 step 3 checkpoint, and groups and swimlanes (M4 step 4, 2026-10-11)
**The owner's decisions on the step 3 checkpoint (2026-10-11):**

Lanes follow the picture's direction: **columns** (side by side) for a picture that runs top to bottom, **rows** (one above the other) for one that runs left to right.
2. **Labels after a layout:** a label a moved line now cuts through is rewritten with `auto`, as step 3 does (D80). Kept.
3. **Orthogonal edges whose ends now line up** become `--`: approved.
4. **New: an opt-in "Allow reordering statements" option** in the Layout panel. When on, the layout may move a node's statement later in the code, only when that is safe (nothing earlier depends on its position, and the drawing order doesn't change visibly), when that lets it be written as a clean relation instead of a long distance or a diagonal (`se-218730`'s `below=20cm of init`). Off by default. **Scheduled for step 7** (the owner left step 4 or 7 open): it builds on the layout planner, and step 4 changes what "safe" means (a node must stay before the background block whose fit lists name it), so it is designed once, after lanes exist.

**Step 4: groups and swimlanes** (`src/edit/lanes.ts`, `src/ui/grouppanel.tsx`):
- **What is written.** A group: `\node[group, fit=(a) (b), label={[group title]north:Title}] (title) {};` on the background layer. A lane, in form B: `\node[lane, fit=(a) (b) (a |- lanes top) (a |- lanes bottom), label={[lane title]north:Customer}] (customer) {};` for columns, `(a -| lanes left) (a -| lanes right)` and a title on the `west` side for rows. The first lane of a picture writes the two shared coordinates, `\coordinate (lanes top) at (a.north);` and `\coordinate (lanes bottom) at (e.south);`. Everything goes into one `\begin{scope}[on background layer]` block at the end of the picture (or the existing one), **with the coordinates inside it**, where the sample shown to the owner had them just before it: the whole block is then one unit that new nodes go before. Styles the document lacks are added where it keeps its styles (`lane`: `draw=gray!60, fill=gray!8, rounded corners=2pt, inner sep=3mm`; `lane title`: `font=\bfseries\small`; `group`: `draw=gray!70, dashed, rounded corners=3pt, inner sep=3mm`; `group title`: `font=\small`); a document's own `lane` or `group` style is used as it is. `fit` and `backgrounds` are loaded (D28). Unnamed nodes are named from their labels first, as for chains (D79).
- **Row titles are not rotated.** A rotated title (`rotate=90, anchor=south`) is the usual BPMN look, but the quick preview doesn't draw rotated nodes (`rotate` is "unrendered"), so the title would be drawn in the wrong place until the TeX picture arrives. Rows get a horizontal title to their left; rotated titles can follow if the owner wants them.
- **Reading lanes** works on any code in this form, the user's own included: a lane is a fit node whose list lines a member up with exactly two coordinates through one operator (`|-` for columns, `-|` for rows); fit nodes that line up with the same two coordinates are one set, ordered across. Other fit nodes are groups.
- **The panel.** With nodes selected: **Group**, **New lane** (an optional title for either), **Move to lane** (with a list of the set's lanes), **Add to** a selected group or lane, **Take out of** the groups and lanes that list them. With a group or lane selected: what it holds, and its **Title** (set, change or remove). A lane or node can't be left empty: the panel says to delete it instead.
- **Dropping a node into another lane** moves it there in the same undo step as the move. Lanes are bands: for columns only the drop's x counts, so a node dropped below the lanes still joins the lane above it.
- **Upkeep.** After every visual edit (`applyEdit`), and inside the planners that need it (new lanes, membership, auto-layout), a shared coordinate written as `at (member.north)` (`south`, `west`, `east`) is moved to whichever member is at that extreme now, in the same step. Coordinates written any other way are the author's and stay. Typing in the code pane never triggers it.
- **Deleting.** A deleted member leaves its lanes; a line-up that named it (`(a |- lanes top)`) names another member instead, and a shared coordinate at it moves to the next member at that extreme. Deleting every lane of a set also removes the two coordinates (unless other code uses them) and the background block it emptied, so the code is as it was before the first lane.
- **New nodes go before a block that holds only fit nodes and coordinates** (`src/edit/insert.ts`), so groups and lanes can list them. This also applies to `self-document.tex`'s fit box. A node defined after a group's statement can't be added to it (TikZ needs it first); the panel says to move its line up.
- **Dragging a lane** moves its members, not the shared coordinates: line-ups aren't members (`fitMemberNames`, used by the group drag of D78).
- **Auto-layout keeps lanes apart** (D80). Lanes across the flow (rows laid out top to bottom, columns left to right) are ELK partitions, so each lane takes the layers after the lane before it. ## D87: Milestone 4 step 7: layout speed and progress, groups by default, reordering, turned nodes, key-named styles, \$, American English (2026-10-11)
**Decision:**

- **"Allow reordering statements" (D81 item 4).** A checkbox in the Layout panel, off by default and not kept between visits. With it, a node the plan places in a roundabout way (a written distance, a diagonal, a shift) because the node it follows in the flow (above it in its column, before it in its layer, or the nearest one an edge comes from in the layer above) comes later in the code has its line moved to just after that node's line, **together with the lines in between that are placed against it or follow it in the flow**, in their order. Safe means: all of them are top-level statements on lines of their own; everything passed is a node statement of the layout or a coordinate (no paths, scopes, styles or other commands, so the drawing order changes only among nodes the layout keeps apart); nothing that stays in between names a moved node; the node it now follows doesn't name one; no chain nodes; and after each move every node is exactly where it was, with no new syntax errors. The plan is then made again in the new code order (ELK's result is kept: named nodes keep their ids). A compile that finishes after its tab was left is dropped. The selection, a drag or a label being typed are dropped on a switch; the view is fitted again.
- **Storage** (`src/ui/kv.ts`): one IndexedDB record per tab, `doc:<id>` (`DocRecord` in `src/ui/docs.ts`: the old session's fields plus `id`, `title`, `created` and `rev`), the file handle under `handle:<id>`, and Recently closed under `closed:<id>`. An empty tab is not stored until it has text, and empty records are dropped at start. The single session of before tabs (`session`, `previous`, `handle`) is moved once, in one transaction: the session becomes a tab (with its handle), the work put aside goes to Recently closed as "Previous work", and the old keys go. The home page's Continue your diagram names the most recently edited tab and how many others hold work.
- **Opening opens a tab:** Open, dropping a file, Import, Paste TikZ, a share link (at start or pasted into the address bar), a template link from the home page, and New. The tab on screen is reused only when it is empty (the start screen), and then undoably, as before. "Restore previous work" and putting work aside are gone (D74, D77 item 5, D95). A tab is named after its file, else a title: the template's, "Shared diagram", "Pasted diagram", "Mermaid import", "DOT import", "Untitled".
- **Closing a tab** (×, or a middle click) keeps it in **Recently closed** (the clock button after the tabs) when it holds work, with its file handle; the last 20 are kept; reopening opens a new tab. An empty tab or an untouched template is simply closed. Closing the last tab leaves an empty one (the start screen). There is no confirmation, since nothing is lost.
- **Two browser windows (or browser tabs) on the same diagrams.** All windows show the same set of tabs, read from IndexedDB, and each shows one of them.
  - **One writer per diagram:** a window may edit a tab only while it holds that tab's Web Lock (`navigator.locks`, `tikzflow-tab:<id>`), and it holds just one: the tab on screen's. Switching away saves the tab and lets go of its lock.
  - **The same tab in a second window** is shown read-only: an amber banner says so, the code pane is read-only, the canvas only selects and pans, and every edit path (`applyEdit`, `replaceDocument`, creating nodes, labels, layout) refuses with that reason. It follows the first window's saves as they land (a `BroadcastChannel` says which tab changed; its record is read again).
  - **Edit here** asks the editing window to save and let go, then takes the lock and the latest version. If that window doesn't answer within 3 s (frozen), the lock is taken by force; the frozen window, when it wakes, saves what it hadn't under the rule below.
  - **When the editing window closes or switches away,** a read-only window in front takes the tab over by itself: on the broadcast, on focus, or at its next look (every 10 s; a window that closes sends nothing, and its lock is freed a moment after).
  - **A second window starts** on the tab it showed before a reload (kept per window in sessionStorage), else on the most recently edited tab no other window has open, else on a new empty tab, so it never opens on top of the first window's diagram (`startTab`). A small dot marks tabs that another window has open.
  - **No blind overwrites, as a second line of defense:** every write names the revision it replaces and is checked in the same IndexedDB transaction (`writeDoc`). If another window wrote meanwhile (a browser without Web Locks, a lock taken by force), nothing is overwritten: the tab takes the other window's version, and this window's version goes to a new tab "… (your copy)", with the undo history, which is then shown. The status bar says so.
  - **Before tabs,** two windows both autosaved the one session and the last one to write won, silently. This design removes that race.
- **An interrupted page close.** The tab on screen is saved 0.5 s after its last change, on every tab switch, and when the page is hidden or closed (`visibilitychange`, `pagehide`). IndexedDB may not finish a write that starts as the page goes, so at those moments every tab with unsaved changes is also written synchronously to localStorage (`tikzflow.journal.<id>`: the record, the revision it replaces, and a fingerprint). The journal entry is removed once IndexedDB has that exact version. At the next start, before anything else, each journal entry is compared with the stored record (`journalAction`): stored if the write never landed, dropped if it did, and kept as a separate tab "… (recovered)" if the diagram was changed since by another window (a status message names it). Entries of tabs another window has open are left for that window. What can still be lost: edits from the last half second before a browser crash or power cut (no event fires), and anything when the browser refuses storage altogether (a private window that refuses IndexedDB keeps the work in the page only, as before).
- **The engine stops while the tab is hidden** (D69 item 4): after 15 s hidden the engine worker (about 330 MB) is stopped; it starts again when the tab is shown, and recompiles only if the code changed. A quick look at another tab keeps it.
- **The tab bar** sits in the app bar where D92 left room: tabs (role `tablist`, ←/→ move between them), +, and Recently closed. The active tab's name carries the ● for unsaved file changes (it has the old `file-name` test id).

**Why:** SPEC Milestone 5 ("Multiple tabs… Each tab keeps its own code, undo history, autosave and preview. Opening a file, an import or a share link opens in a new tab instead of putting the current work aside"), D86 item 5, D69 item 4, and the owner's instruction that losing work is release-blocking, which asked for two windows and an interrupted close to be handled explicitly.

**Decision (the bug):**
- **The cause, confirmed by pdfTeX.** A new probe, `spike/engines/probes/p12-diagonal-anchors.tex`, puts a box on each corner of every shape the preview draws (`below right=of`, `above left=of` and so on), thick and thin, with minimum sizes, turned borders, and the template's own I/O node with the drag's result. `npm run fidelity` now also compares the four diagonal anchors of every node (`corners` in `fidelity.json`; the summary line counts them).   - **Trapezium:** pgf's `north east`, `south east` and the others are where the 45° ray from the center meets the border, not the corners (`pgflibraryshapes.geometric`). The preview used the corners: 23pt to the side for the template's I/O node. Also, pgf finds every compass anchor on a border whose corners are moved out by the outer sep along their miters (the preview scaled the polygon), casts `base east` and `mid east` from the base and mid points, rounds `shape border rotate` to a multiple of 90° as pgf does, and has `left side`/`right side`/`top side`/`bottom side` as the midpoints of that border's sides (east and west of a turned trapezium were wrong before).

  - **Rounded rectangle:** its width is the text, the inner xsep and the chord the text's half height cuts from the end arcs (it was text plus half the height: 5pt too wide); a minimum width gives the whole width less twice the inner xsep, pgf's own reckoning, checked; the diagonals are where the arcs meet the straight sides, not the box's corners.
  - **Cylinder:** sized as pgf sizes it (end radius aspect × half height; the text reaches into the bottom's ellipse; half the line width added; `minimum height` along the axis, `minimum width` across, whatever the turn). Its ends differ, so **the shape is drawn off its text's center** (`NodeShape.shift`; pgf's `shape center` anchor); a cylinder turned 270° has its top at the bottom (`axis`). Anchors are found on its real border (straight sides and the ends' half ellipses); `shape center`, `top` and `bottom` are known. A lying cylinder was 9.5pt too narrow and its neighbors 12pt off.
  - Rectangle, rounded corners, circle and diamond were already right.

Against the old `shapes.ts` 41 of its cases fail.

**Decision (the safeguard): TeX reports where it put each node; the editor flags disagreement, it doesn't correct it.**
- **The report.** The preview's compile input defines `\tikzflowplace` on its first line and calls it for every named node of the layout (statement nodes, group and lane boxes, chain nodes; not locked ones nor made-up names; plain names with single spaces) just before `\end{tikzpicture}`, on that same line, so no line numbers move. - **The flag:** a small amber marker on the node; with the node selected, TeX's box dashed, so the gap is visible; and a note in the TeX preview's notes naming the nodes and the worst distance, saying outlines and positions written next to them may be off, that a point or two comes from estimated text widths, and to report anything more.
- **Why not correct:** a mismatch says that the editor's geometry for a node is wrong, not what the right geometry is. Every relation a drag writes (`below right=7mm and 1.8cm of read`) is worked out from that geometry, and edges, guides and handles too, so moving the native drawing onto TeX's box would only hide the cause while the code still came out wrong. The flag tells the user where not to trust the editor and gives us the case to fix.
- **How much it would flag today:** the templates, none. The corpus (hand-written TeX from the web): 50 nodes in 9 of 28 pictures, mostly 1–3pt from estimated text widths adding up along a chain of relations, a few more where matrices, `\resizebox` or chains are involved (up to 16pt). The owner asked for 1pt; the wording is kept quiet for that reason. A decision for the owner: keep 1pt, or flag only beyond 2–3pt.

## D103: The drag benchmark and the baseline (M6 step 0, 2026-10-12)
**Decision: how drags are measured** (`npm run drag:bench`, `scripts/drag-bench.ts`):
- **What runs:** a production build served by `vite preview`, in Edge with a window (not headless, so frames are paced and drawn as for a user), 1920×1080 CSS pixels at 1.5× (a large window on the owner's 3840×2160 screen at 150%, 60 Hz), service workers blocked so the engine's background download doesn't run during a drag. Each picture opens from a share link; the view is fitted, then zoomed with the wheel until the dragged node is 28–40 px tall. The pictures (`scripts/lib/benchpictures.ts`, also `npm run layout:bench -- --picture=…`): the 200-node, 250-edge one (dragging `n100`), and, measured only, a 500-node, 600-edge one (`n250`) and the dense 4–16–16–4 network written out (`l1n7`). Both now start with `\usetikzlibrary{positioning}`: without it TeX stopped with 100 errors, so the TeX preview had never drawn them.
- **Two runs per interaction**, each followed by Ctrl+Z:
  - **A 125 Hz mouse** (the target's measure): 180 moves 8 ms apart, sent straight to the browser through the DevTools protocol without waiting for each to be handled (Playwright's `mouse.move` waits, which lets a slow page set the pace). The page records every animation frame; a frame is on time when its interval is within 16.7 ms plus 10% (two frames for 30 fps). Long tasks (over 50 ms) are observed. **The drop** is timed from `pointerup` (a capturing listener on the window, so before the canvas's handler) to the frame after it.
  - **One update at a time, traced:** 30 moves, each sent only after the page has drawn the frame of the one before (two animation frames); a Chromium trace splits the main thread's time per move (its handler, the render, and that frame's style, layout and paint) and by kind (script, style, layout, paint, GC). This is the cost of one drag update whatever the browser does with input, and what step 2 works on.
- **The CPU slowdown** is the DevTools protocol's `Emulation.setCPUThrottlingRate`, set only around the drag.
- `--profile` drags once in a build that isn't minified, with source maps, and prints a CPU profile by source and function and the trace's breakdown. `--label=<name>` saves `spike/perf/results/<name>.json` (the baseline: `baseline.json`).

**Found while building it: Edge doesn't hold mouse moves back to one per frame.** A plain test page (a `pointermove` handler that takes 30 ms, a 125 Hz stream of moves) got 49 moves handled and 10 frames drawn in 1.5 s: each move is handled as it comes, and drawing waits. The editor handles every move in full (layout, edges, a Preact render of the whole canvas), so at 125 Hz it falls behind and draws a frame every few hundred milliseconds. This is the first thing step 2 fixes: work once per frame, with the latest pointer position.

1. **No frame pacing** (above): every move does the whole update.
2. **The whole picture is laid out again** on every move (`layoutDocumentPicture` with the drag's override, 8 ms in Node, and the edge model on top), although dragging `n100` changes only it and the nodes that follow it.
3. **The whole canvas is rendered again:** Preact compares and rewrites every node, edge and label element (`setAttribute` is the largest single item after the browser's own work), so the browser repaints the whole canvas (paint is as large as all the script).
4. **With the TeX preview,** the stale patch (D96) is worked out for the whole picture on each move (`stalepatch.ts`, 122 ms over a 1.5 s drag), and TeX's own picture (about 23,600 elements on the page with the 200-node picture) doubles style and paint.
5. **The code pane forces a layout of the whole page:** CodeMirror reads the browser's selection when it measures (after a selection change, and on the drop's edit), and reading it makes the browser lay out the page first (`get anchorNode`, 190 ms in the profile).

The drop needs the edit's own re-analysis and render to be cheaper, and the group drop's planning batched.

**Why:** D102 (measure before and after; a concrete target).

## D105: Placement links, Detach, and dragging only the dragged node (M6 step 1, 2026-10-13)
**Decision:**
- **What a link is** (`src/edit/links.ts`, `placementLinks`): node B follows node A when B's own placement names A (`below=of A`, `at (A |- C)`, `at (A.east)`), resolved as TikZ does (the latest A defined before B). **Not links**, and left to follow as they always have: a group or lane box around its members (`fit`), the coordinates a set of lanes shares (D81), and nodes on a path (edge labels follow their edge). These are "follows by design" (`followsByDesign`).
- **Cutting a link never moves anything.** The node that loses its link is placed again where it stands (`planMove` with the new `exact` option): the emitter's usual order, but a candidate counts only if it lands within ALIGN_EPS (0.5 pt) of where the node is; when whole millimetres don't reproduce the place, the same form is tried with tenths (`below=2.53cm of start`, `formatDistance(pt, true)`); coordinates (two decimals of the unit, a third if needed) are the last resort. The new `prefer` option tries named targets first, on their own and at any distance (the 5 cm limit on straight relations doesn't apply to them), so a follower goes to what the dragged node hung off (`small` from `below=of read` to `below=2.53cm of start`).
- **Unlink** (`planUnlink`): one link, either way (the node stops following A, or follower B stops following the node). **Detach** (`planDetach`, one node or a selection): every link both ways: the nodes placed against them are re-attached (to what the detached nodes were placed against first) or pinned, then each detached node gets its position as coordinates. Both are checked by laying the picture out: every node other than boxes, lane coordinates and path nodes stays within 0.5 pt, or the edit is refused with the node named.
- **Chains** (D79): a follower placed by a chain is rewritten only after its chain is written out, in the same undo step (`Work.unchain`); ids that change are mapped through.
- **Detach from style** (`src/edit/detachstyle.ts`): the style's keys replace its name in the node's options, in place, which is how TikZ applies a style, so the node looks the same; document styles inside it are expanded too, `#1` takes the node's argument or the style's `.default`; a key the node sets again later in its own options (only keys where the last value wins: fill, draw, font, sizes and so on) is left out. Refused, with the reason, for styles written with `/.code`, `/.style 2 args`, `/.estyle` or `/.prefix style`, and for styles that use themselves. Checked: every node's position, size, colors, line and text measures are unchanged.
- **Dragging (D104)**: only the dragged node moves. During the drag its followers (by `movingWith`, less the by-design ones) are held where they are with the drag's overrides, so the preview shows the result; on the drop, the move is planned as before, then `keepInPlace` puts back every other node that moved, earliest in the code first, re-attached or pinned, until nothing else moved, and both go in as one undo step. The status bar adds "Kept in place: small (below=2.53cm of start)". If a node that would move along can't be rewritten (it is locked, or in a block kept as it is), the drop is refused and the status bar says to hold Ctrl (⌘) to move it along. A chain drag (D79), the pin of a node locked by an undefined name, and group drags (members and their boxes may move; prefer what the members hung off) do the same.
- **Ctrl (⌘ on a Mac)** during a node or group drag flips the mode, checked on every move and on Ctrl's keydown and keyup, so pressing or releasing it mid-drag switches at once. The toolbar switch **Move followers too** (`moveFollowers` in `store.ts`, localStorage `tikzflow.moveFollowers`) flips the default. While dragging, followers get a faint outline (`FollowerMarks`): dashed when they stay, solid when they move along.
- **The panel's Placement section** (`LinksPanel` in `inspector.tsx`): "Follows read: `below=of read`" with Unlink for each; "small and base are placed relative to this…" and each follower with Unlink; Detach (disabled with a reason when there is nothing to cut). With several nodes, Detach N nodes. **Detach from <style>** buttons sit under the "This node / All process nodes" choice, one per style the selected nodes all name.
- **The toolbar is one row from 1,500 px up** (it was 1,366, D101): the labelled switch takes 131 px. Nothing is cut off from 1,100 px up (the D101 checks pass); below 1,500 the second group drops to its own row, as D101 allowed. An icon-only switch would keep 1,366; the label was kept because the owner named the switch.
- **Help:** "Editing on the canvas" has "Only the node you drag moves" and "What a node follows"; "Colors, fonts and styles" has Detach from style. The `?` list's Ctrl-drag entry says what it does on a node.

**Tests:** `test/links.test.ts` (12: links, Unlink both ways, Detach, keeping followers, the tenths, Detach from style and its refusal); `test/golden-links.test.ts` (151: on every corpus picture and template, the first node with followers and the first one that also follows something, each moved alone and detached; every other node stays within 0.5 pt; 148 golden files in `test/fixtures/golden/links/`, no refusals); `test/e2e/links.spec.ts` (9). **One expectation changed:** `toolbar.spec.ts` "one row from 1366 px" became "from 1500 px" (above). No other test or golden file changed: existing move goldens call `planMove` directly, which works as before.

**Known limits:**
- Distances written to keep a node exactly in place can have a tenth (`2.53cm`), where a person might round.
- Dragging a picture's first node away pins its followers: nothing earlier in the code can hold them.
- Snapping doesn't line up with followers that stay put (it never used a node's followers).
- The drop lays the picture out once per rewritten node: step 2 measures it.

**Why:** D102 (the owner's addition) and D104 (the owner's decisions on the dragging default).

## D106: A Venn diagram template, under "Other diagrams" (M6 step 1b, 2026-10-13)
**Decision:**
- **One three-set template, not two.** Three sets show every kind of region (each set alone, each pair, all three), and a two-set diagram is this one with a circle and three counts deleted (Delete re-attaches what was placed against them, D56). Two near-identical cards would crowd the gallery.
- **Circle nodes filled at 30% opacity, not `\clip`.** The idiomatic way to shade an intersection is `\begin{scope}\clip (a) circle (2cm); \fill (b) circle (2cm);\end{scope}`, and the editor keeps a `\clip` scope as a locked block: the template wouldn't open fully editable, which every template must (D95). Teaching the editor clipped regions (drawing them, selecting them, keeping them when a circle moves) is a feature of its own, well beyond a template step. With `fill opacity=0.3` each set is an ordinary circle node, so every set can be dragged, resized, recolored and detached, and the overlaps' colors come from the browser and TeX blending the fills. What it can't do: give one overlap a color of its own (it is always the mix of its sets' colors).
- **The code** (`src/templates/venn.tex`): `set`, `set name` and `count` styles; the circles placed `on grid`, so distances are between centers (b 24 mm right of a; c below right of a, making an equilateral triangle); set names outside the circles and a count in each of the seven regions, each placed against a circle. Names are plain words with hyphens (`only-a`, `ab`, `abc`), so the fidelity harness and TeX's placement report (D98) cover them all.
- **Checked like every template:** fully understood and editable (no locks, unknown keys, notes or undrawn options; every node draggable), compiled by our engine into a committed thumbnail (`src/site/thumbs/venn.svg`, `fill-opacity="0.3"` in TeX's SVG) and by pdfLaTeX in CI, and 13 of 13 nodes within 1 pt of pdfTeX (`npm run fidelity`: 576 of 663 nodes overall, the Venn's 13 added, nothing else changed).
- **"Other diagrams"** is a second gallery heading (`OTHER_SECTION` in `catalog.ts`), after Neural networks, in the home page's gallery, the New menu and the start screen ("Thirteen flowcharts and diagrams").

**Tests changed** (the template count and the second heading): `test/templates.test.ts` (13 templates; the headings list has Other diagrams; two `tgroup` headings; and **every template has edges except the Venn diagram**, which is sets only), `firstrun.spec.ts` (13 cards, both headings), `site.spec.ts` (13 cards, both headings), `templates.spec.ts` (14 cards in New with the blank one, both headings and the first card under each, the Venn's headline "13 nodes and 0 edges editable"), `test/live/live.spec.ts` (13 thumbnails, 14 cards).
